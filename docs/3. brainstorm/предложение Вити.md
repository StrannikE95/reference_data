В PostgreSQL можно сделать общую таблицу с колонкой type / type_id и партиционировать её по этой колонке. Обычно для этого используют LIST-партиционирование.
Партиционирование по типу действительно позволяет хранить разные типы в разных физических партициях и даже раскладывать их по разным tablespace/дискам

Например, есть справочник типов:
CREATE TABLE object_types (
    id   integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code text NOT NULL UNIQUE
);

И общая таблица данных:
CREATE TABLE objects (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    type_id    integer NOT NULL REFERENCES object_types(id),
    data       jsonb NOT NULL DEFAULT '{}',
    created_at timestamptz NOT NULL DEFAULT now(),

    PRIMARY KEY (type_id, id)
)
PARTITION BY LIST (type_id);

Партиции:
CREATE TABLE objects_type_1
    PARTITION OF objects
    FOR VALUES IN (1);

CREATE TABLE objects_type_2
    PARTITION OF objects
    FOR VALUES IN (2);

CREATE TABLE objects_type_3
    PARTITION OF objects
    FOR VALUES IN (3);

Можно сразу задавать tablespace:
CREATE TABLE objects_type_1
    PARTITION OF objects
    FOR VALUES IN (1)
    TABLESPACE fast_ssd;

CREATE TABLE objects_type_2
    PARTITION OF objects
    FOR VALUES IN (2)
    TABLESPACE cheap_hdd;

### USER
можно ли в PostgreSQL FK прописать из JSONB?
типа мы же можем строить btree индексы по полям JSONB (функциональные и частичные), а можем ли мы аналогично построить внешние ключи из полей JSONB на условно id колонку таблицы или даже на поле другого JSONB? 

### ASSISTANT
Коротко: **напрямую — нет**. В PostgreSQL нельзя объявить `FOREIGN KEY` на выражение вида `data->>'user_id'` или на путь внутри `JSONB`. Но можно сделать это **косвенно через вычисляемую/сгенерированную колонку**, и тогда внешний ключ будет работать.

---

## Почему функциональный индекс не решает задачу

Вы действительно можете создать индекс по выражению из `JSONB`:

```sql
CREATE INDEX ON orders ((payload->>'user_id'));
```

или даже уникальный функциональный индекс:

```sql
CREATE UNIQUE INDEX ON accounts ((data->>'ext_id'));
```

Но `FOREIGN KEY` в PostgreSQL привязывается не к индексу и не к выражению, а к **реальным колонкам таблицы**.

То есть такое не сработает:

```sql
-- НЕЛЬЗЯ
ALTER TABLE orders
ADD CONSTRAINT orders_user_fk
FOREIGN KEY ((payload->>'user_id')) REFERENCES users(id);
```

PostgreSQL не поддерживает декларативные внешние ключи по выражениям.

---

## Правильный способ: сгенерированная колонка

Начиная с PostgreSQL 12 можно использовать `GENERATED ALWAYS AS ... STORED`.

Например, есть родительская таблица:

```sql
CREATE TABLE users (
    id bigint PRIMARY KEY,
    name text
);
```

И есть дочерняя таблица, где `user_id` лежит внутри `JSONB`:

```sql
CREATE TABLE orders (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL,

    user_id bigint GENERATED ALWAYS AS (
        (payload->>'user_id')::bigint
    ) STORED,

    CONSTRAINT orders_user_id_fkey
    FOREIGN KEY (user_id)
    REFERENCES users(id)
);
```

Теперь при вставке строки значение `payload->>'user_id'` автоматически материализуется в колонку `user_id`, и уже на неё действует обычный внешний ключ.

Пример:

```sql
INSERT INTO orders (payload)
VALUES ('{"user_id": 1, "amount": 100}');
```

Если `users.id = 1` нет, вставка упадёт с ошибкой внешнего ключа.

---

## Если ключ хранится вложенно внутри JSONB

Можно использовать `#>>`:

```sql
CREATE TABLE orders (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL,

    user_id bigint GENERATED ALWAYS AS (
        (payload #>> '{user,id}')::bigint
    ) STORED,

    CONSTRAINT orders_user_id_fkey
    FOREIGN KEY (user_id)
    REFERENCES users(id)
);
```

Для такого `JSONB`:

```json
{
  "user": {
    "id": 42
  }
}
```

колонка `user_id` будет равна `42`.

---

## Если родитель тоже хранит ключ внутри JSONB

Да, можно сделать внешний ключ из поля одного `JSONB` на поле другого `JSONB`, но опять же через сгенерированные колонки.

Например:

```sql
CREATE TABLE accounts (
    id bigint PRIMARY KEY,
    data jsonb NOT NULL,

    ext_id text GENERATED ALWAYS AS (
        data->>'ext_id'
    ) STORED,

    CONSTRAINT accounts_ext_id_key UNIQUE (ext_id)
);
```

Дочерняя таблица:

```sql
CREATE TABLE events (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    data jsonb NOT NULL,

    account_ext_id text GENERATED ALWAYS AS (
        data->>'account_ext_id'
    ) STORED,

    CONSTRAINT events_account_ext_id_fkey
    FOREIGN KEY (account_ext_id)
    REFERENCES accounts(ext_id)
);
```

Теперь:

```sql
INSERT INTO accounts (id, data)
VALUES (1, '{"ext_id": "acc-100"}');

INSERT INTO events (data)
VALUES ('{"account_ext_id": "acc-100"}');
```

будет работать.

А такая вставка упадёт:

```sql
INSERT INTO events (data)
VALUES ('{"account_ext_id": "unknown"}');
```

## Можно ли сделать FK на целый JSONB-столбец?

Технически да, если речь идёт не о пути внутри `JSONB`, а о целом столбце типа `jsonb`.

Например:

```sql
CREATE TABLE parent_json (
    id bigint PRIMARY KEY,
    ref jsonb UNIQUE
);

CREATE TABLE child_json (
    id bigint PRIMARY KEY,
    parent_ref jsonb REFERENCES parent_json(ref)
);
```

Для `jsonb` есть операторы равенства и поддержка B-tree, поэтому такой внешний ключ возможен.

Но это редкий и обычно плохой сценарий. Обычно нужно ссылаться не на весь документ, а на конкретное значение внутри него: `id`, `uuid`, код, внешний идентификатор и т.п. Для этого лучше извлекать скалярное значение в отдельную колонку.

## Важные ограничения и нюансы

### 1. Выражение должно быть иммутабельным

Для сгенерированной колонки выражение должно быть `IMMUTABLE`.

Операторы и функции вроде:

```sql
data->>'key'
data #>> '{a,b,c}'
jsonb_typeof(...)
```

обычно подходят.

Но нельзя использовать подзапросы, изменяющиеся функции, обращения к другим таблицам и т.п.

---

### 2. Типы должны совпадать или корректно приводиться

Если родительский ключ `bigint`, то и сгенерированная колонка должна быть `bigint`:

```sql
(payload->>'user_id')::bigint
```

Если родительский ключ `uuid`:

```sql
(payload->>'user_uuid')::uuid
```

Если родительский ключ `text`:

```sql
payload->>'account_code'
```

Не стоит смешивать типы без необходимости.

---

### 3. Если значение отсутствует, будет NULL

Для:

```sql
payload->>'user_id'
```

если ключа нет, результат будет `NULL`.

Внешний ключ допускает `NULL`, поэтому такая строка не будет проверяться на существование родителя.

Если вы хотите, чтобы поле было обязательным, нужно дополнительно это контролировать, например:

```sql
ALTER TABLE orders
ALTER COLUMN user_id SET NOT NULL;
```

или добавить `CHECK` на исходный `JSONB`:

```sql
ALTER TABLE orders
ADD CONSTRAINT orders_payload_has_user_id
CHECK (payload ? 'user_id');
```

Но нужно понимать, что `payload ? 'user_id'` проверяет наличие ключа, а не то, что там обязательно корректный `bigint`.

---

### 4. Нужно быть аккуратным с некорректными данными

Если внутри `JSONB` лежит строка, которую нельзя привести к `bigint`, будет ошибка.

Например:

```json
{"user_id": "abc"}
```

при выражении:

```sql
(payload->>'user_id')::bigint
```

приведёт к ошибке.

Если данные могут быть неоднородными, можно сделать более осторожное выражение, например:

```sql
user_id bigint GENERATED ALWAYS AS (
    CASE
        WHEN payload->>'user_id' ~ '^-?[0-9]+$'
        THEN (payload->>'user_id')::bigint
    END
) STORED
```

Но тогда для некорректных значений будет `NULL`, а не ошибка. Если вам нужна строгая валидация, лучше проектировать данные так, чтобы тип был гарантированно корректным.

---

### 5. JSONB-массивы идентификаторов так не подключить

Если у вас в `JSONB` хранится массив идентификаторов:

```json
{
  "user_ids": [1, 2, 3]
}
```

то обычный внешний ключ на этот массив повесить нельзя.

`FOREIGN KEY` работает с колонками, а не с элементами массива внутри `JSONB`.

В этом случае нужно нормализовать данные:

```sql
CREATE TABLE order_users (
    order_id bigint NOT NULL REFERENCES orders(id),
    user_id bigint NOT NULL REFERENCES users(id),
    PRIMARY KEY (order_id, user_id)
);
```

И заполнять эту таблицу либо из приложения, либо триггерами из `JSONB`.

---

### 6. Частичные индексы не заменяют частичные внешние ключи

Вы можете сделать частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX ON accounts ((data->>'ext_id'))
WHERE data ? 'ext_id';
```

Но внешний ключ не может ссылаться на частичный уникальный индекс.

Если вам нужна логика вида:

> если поле есть — оно должно ссылаться на существующего родителя, а если поля нет — ничего не проверять,

то через сгенерированную колонку это обычно решается так:

- если поля нет, сгенерированная колонка равна `NULL`;
- `NULL` во внешнем ключе не проверяется;
- если поле есть, значение должно существовать в родителе.

Но если нужна более сложная условная логика, придётся использовать триггеры или приложение.

---

### 7. Действия `ON UPDATE`/`ON DELETE SET NULL` с генерируемыми колонками имеют ограничения

Если дочерняя колонка сгенерирована из `JSONB`, PostgreSQL не может просто взять и изменить её в дочерней строке, потому что она всегда вычисляется из выражения.

Поэтому с генерируемыми ссылочными колонками обычно хорошо работают простые варианты:

```sql
FOREIGN KEY (...) REFERENCES ... RESTRICT
FOREIGN KEY (...) REFERENCES ... NO ACTION
FOREIGN KEY (...) REFERENCES ... ON DELETE CASCADE
```

А вот действия, которые пытаются изменить дочернюю колонку, например:

```sql
ON DELETE SET NULL
ON UPDATE CASCADE
ON UPDATE SET NULL
```

могут быть недоступны или не иметь смысла в зависимости от версии и конкретной схемы. Это нужно проверять на вашей версии PostgreSQL.

## Альтернатива: обычная колонка + триггер

Если у вас старая версия PostgreSQL без сгенерированных колонок или нужна нестандартная логика, можно сделать обычную колонку и заполнять её триггером:

```sql
CREATE TABLE orders (
    id bigint PRIMARY KEY,
    payload jsonb NOT NULL,
    user_id bigint,

    CONSTRAINT orders_user_id_fkey
    FOREIGN KEY (user_id)
    REFERENCES users(id)
);

CREATE FUNCTION orders_set_user_id()
RETURNS trigger AS $$
BEGIN
    NEW.user_id := (NEW.payload->>'user_id')::bigint;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER orders_set_user_id_trg
BEFORE INSERT OR UPDATE OF payload ON orders
FOR EACH ROW
EXECUTE FUNCTION orders_set_user_id();
```

Но это уже менее декларативно и требует больше контроля.

## Итог

**Напрямую** сделать внешний ключ из выражения над `JSONB` нельзя:

```sql
FOREIGN KEY ((data->>'user_id')) REFERENCES users(id)
```

— так нельзя.

**Но можно** сделать сгенерированную колонку:

```sql
user_id bigint GENERATED ALWAYS AS (
    (data->>'user_id')::bigint
) STORED
```

и уже на неё повесить внешний ключ:

```sql
FOREIGN KEY (user_id) REFERENCES users(id)
```

Если родитель тоже хранит ключ в `JSONB`, нужно аналогично извлечь его в сгенерированную колонку и сделать на ней `PRIMARY KEY` или `UNIQUE`.

То есть схема такая:

```text
JSONB-поле
  -> сгенерированная колонка
    -> обычный FOREIGN KEY
```

Это единственный нормальный встроенный способ получить декларативную ссылочную целостность из данных внутри `JSONB`.
