# 1 (Несколько	Стандартный составной	Типизированные	Снимок)
Особенности:
+ Секционирование для разделения редакций справочника
+ Смысл Снимка = Секция на редакцию даёт целый согласованный набор таблиц
+ Выборки и связи настоящие и изолированы внутри секции 

Хорошо: 
+ Валидация полей - работает
+ Поиск (без FK) - быстрый
+ Поиск (с FK) - быстрый

Плохо:
- Размер таблицы - большой (много избыточного дублирования)
- Создание / изменение метаданных = SQL

Пример. У материала две своих колонки: `is_bearing` (несущая) и `density` (кг/м³). 20.10.2026 у кирпича сменилось имя и добавился металл. Редакция 2 хранит полный список, в том числе камень, дерево и брус, которые не менялись. Связь `wall_material (version_id, kind_code) → wall_kind (version_id, kind_code)`.

# 2 (Несколько	Подзарпос: Код + Дата	Типизированные	Интервал)
Особенности:
+ Смысл Интеравала = только экономия места таблицы. => Окупается только на больших наборах данных
+ Нет прямых ссылок. Вместо FK будет код соседней таблицы и дата, на которую надо найти валидное значение кода. 

Хорошо: 
+ Размер таблицы - минимальный (отсутствие избыточного дублирования)
+ Валидация полей - работает
+ Поиск (без FK) - быстрый

Плохо:
- Поиск (с FK) - медленный
- Создание / изменение метаданных = SQL

Пример. Та же правка, но строки, которые не менялись, в таблице один раз. Номера редакции нет. Сосед ищется по коду и дате: у `STEEL` код вида `METAL`, на 2026-10-20 у этого кода открыт интервал в `wall_kind`.

# 3 ("Несколько + 1 историческая"	"Стандартный AS IS + Подзарпос: Код + Дата"	"Типизированные + Jsonb для истории" Снимок)
Особенности:
+ 2 таблицы для разделения актуальной и исторических редакций справочника: актуальная версия - классические типизированные таблицы AS IS; исторические версии - в 1 таблице с jsonb - полем
+ Максимальная скорость выборки по актуальным данным

Хорошо:
+ Поддержка "ломающих" изменений метаданных таблиц в разных редакциях
+ Валидация полей - работает
+ Поиск по актуальным данных (без FK) - быстрый
+ Поиск по актуальным данных (с FK) - быстрый

Плохо:
- Создание / изменение метаданных = SQL
- Требуется по 2 таблицы на 1 справочник
- Поиск по историческим данных (без FK) - медленный
- Поиск по историческим данных (с FK) - медленный
- Размер таблицы - большой (много избыточного дублирования)

Пример. Живые таблицы держат только редакцию 2, связь обычная: `kind_code → wall_kind.kind_code`. Прошлая редакция лежит в одной истории. В редакции 1 у материала ещё не было `kind_code`: документ в jsonb короче, чем сегодняшние колонки.

| STEEL | Сталь | METAL | да | 7850 |

# 4 (Одна	Подзарпос: Код + Дата	Jsonb	Интервал)
Особенности:
+ Смысл Jsonb = динамическая структура
+ Нет прямых ссылок. Вместо FK будет код родителя в текущей таблице и дата, на которую надо найти валидное значение кода. 
+ Секционирование для разделения справочников друг от друга на 1 таблице 

Хорошо: 
+ Создание / изменение метаданных без SQL 
+ Поиск (без FK) - быстрый
+ Размер таблицы - минимальный (отсутствие избыточного дублирования)

Плохо:
- Валидация полей - нет
- Поиск (с FK) - медленный

Пример. Оба справочника лежат в одной таблице. Секция задаётся `dictionary_code`. Поля, кроме кода и срока, сидят в `data`. Родитель — это `parent_code` той же таблицы и дата: у стали родитель `METAL`, его имя берётся из открытого на 2026-10-20 интервала строки `METAL`.

| --- | --- | --- | --- | --- | --- |
| WallKind | STONE | | 2024-01-01 | | `{"name":"Камень"}` |
| WallKind | WOOD | | 2024-01-01 | | `{"name":"Дерево"}` |
| WallKind | METAL | | 2026-10-20 | | `{"name":"Металл"}` |

| WallMaterial | BRICK | STONE | 2026-10-20 | | `{"name":"Кирпич керамический","is_bearing":true,"density":1800}` |
| WallMaterial | TIMBER | WOOD | 2024-01-01 | | `{"name":"Брус","is_bearing":false,"density":500}` |
| WallMaterial | STEEL | METAL | 2026-10-20 | | `{"name":"Сталь","is_bearing":true,"density":7850}` |
