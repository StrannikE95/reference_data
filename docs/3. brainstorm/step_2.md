
# Варианты

1.  N+1 таблиц                  | Колонки = типизированные + version_id         | Версионирование = Снимок, в той же таблице (Вчерашний вариант)
2.  N таблиц                    | Колонки = типизированные + date_from, date_to | Версионирование = Интервал, в той же таблице
3.  N+2 таблиц                  | Колонки = типизированные / jsonb + version_id | Версионирование = Снимок, в отдельной таблице + структура данных, в отдельной таблице
4.  1 таблица на N справочников | Колонки = jsonb + date_from, date_to          | Версионирование = Интервал, в той же таблице



# 1. Когда N таблиц, данных мало / редко меняются, запросы быстрые

Описание:
+ Структура хранения: Несколько отдельных таблиц, типизированные колонки, в PK и FK добавляем version_id. 
+ Версионирование: Актуальные и исторические данные в общей таблице. Тип версионирования = Снимок.

Пример. У материала две своих колонки: `is_bearing` (несущая) и `density` (кг/м³). 20.10.2026 у кирпича сменилось имя и добавился металл. Редакция 2 хранит полный список, в том числе камень, дерево и брус, которые не менялись. Связь `wall_material (version_id, kind_code) → wall_kind (version_id, kind_code)`.

| --- | --- | --- | --- |
| 1 | 2024-01-01 | 2026-10-19 | closed |
| 2 | 2026-10-20 | | active |

`wall_kind`

| version_id | kind_code | name |
| --- | --- | --- |
| 1 | STONE | Камень |
| 1 | WOOD | Дерево |
| 2 | STONE | Камень |
| 2 | WOOD | Дерево |
| 2 | METAL | Металл |

`wall_material`

| version_id | value_code | name | kind_code | is_bearing | density |
| --- | --- | --- | --- | --- | --- |
| 1 | BRICK | Кирпич | STONE | да | 1800 |
| 1 | TIMBER | Брус | WOOD | нет | 500 |
| 2 | BRICK | Кирпич керамический | STONE | да | 1800 |
| 2 | TIMBER | Брус | WOOD | нет | 500 |
| 2 | STEEL | Сталь | METAL | да | 7850 |

Особенности:
+ Секционирование для разделения редакций справочника
+ Смысл Снимка = Секция на редакцию даёт целый согласованный набор таблиц
+ Выборки и связи настоящие и изолированы внутри секции 

Хорошо: 
+ <mark style="background:#90EE90;color:#222">Изолированный набор данных справочника на каждую версию - есть</mark>
+ <mark style="background:#90EE90;color:#222">Механизм поиска по актуальным и истореческим данным - одинаковый</mark>
+ Валидация полей - работает
+ Поиск (без FK) - быстрый
+ Поиск (с FK) - быстрый

Плохо:
- <mark style="background:#FF4500;color:#222">Размер таблицы - большой</mark> (избыточное дублирование при выпуске новой версии)
- Исправление ошибки в справочнике = выпуск новой версии
- Создание справочника - изменение метаданных SQL
- <mark style="background:#FF4500;color:#222">Изменение метаданных - не поддерживается</mark>

# 2. Когда N таблиц, данных много / часто меняются, запросы медленные

Описание:
+ Структура хранения: Несколько отдельных таблиц, типизированные колонки, FK технически отсутствует (используется пара "code записи в таблице" + "дата"). 
+ Версионирование: Актуальные и исторические данные в общей таблице. Тип версионирования = Интервал.

Пример. Та же правка, но строки, которые не менялись, в таблице один раз. Номера редакции нет. Сосед ищется по коду и дате: у `STEEL` код вида `METAL`, на 2026-10-20 у этого кода открыт интервал в `wall_kind`.

`wall_kind`

| kind_code | name | valid_from | valid_to |
| --- | --- | --- | --- |
| STONE | Камень | 2024-01-01 | |
| WOOD | Дерево | 2024-01-01 | |
| METAL | Металл | 2026-10-20 | |

`wall_material`

| value_code | name | kind_code | is_bearing | density | valid_from | valid_to |
| --- | --- | --- | --- | --- | --- | --- |
| BRICK | Кирпич | STONE | да | 1800 | 2024-01-01 | 2026-10-19 |
| BRICK | Кирпич керамический | STONE | да | 1800 | 2026-10-20 | |
| TIMBER | Брус | WOOD | нет | 500 | 2024-01-01 | |
| STEEL | Сталь | METAL | да | 7850 | 2026-10-20 | |

Срез на 2024-06-01: кирпич «Кирпич», брус, камень, дерево. Срез на 2026-10-20: кирпич «Кирпич керамический», брус, сталь, камень, дерево, металл.


Особенности:
+ Смысл Интеравала = только экономия места таблицы. => Окупается только на больших наборах данных
+ Нет прямых ссылок. Вместо FK будет код соседней таблицы и дата, на которую надо найти валидное значение кода. 

Хорошо: 
+ <mark style="background:#90EE90;color:#222">Размер таблицы - минимальный (отсутствие избыточного дублирования)</mark>
+ <mark style="background:#90EE90;color:#222">Механизм поиска по актуальным и истореческим данным - одинаковый</mark>
+ Валидация полей - работает
+ Поиск (без FK) - быстрый

Плохо:
- <mark style="background:#FF4500;color:#222">Изолированный набор данных справочника на каждую версию - нет</mark>
- Поиск (с FK) - медленный
- Создание справочника - изменение метаданных SQL
- <mark style="background:#FF4500;color:#222">Изменение метаданных - не поддерживается</mark>


# 3. Когда N таблиц, запросы по актуальным данным очень быстрые, поддержка изменений схемы данных

Описание:
+ Структура хранения: Несколько отдельных таблиц (эталонная схема без платформенной обвязки), типизированные колонки, станбартный FK.
+ Версионирование: Исторические данные в 1 отдельной таблице, jsonb-колонка под поля с данными, FK технически отсутствует (используется пара "code записи в таблице" + "дата"). Тип версионирования = Снимок.

Пример. Живые таблицы держат только редакцию 2, связь обычная: `kind_code → wall_kind.kind_code`. Прошлая редакция лежит в одной истории. В редакции 1 у материала ещё не было `kind_code`: документ в jsonb короче, чем сегодняшние колонки.

Хорошо:

# 4. Когда 1 таблица

Описание:
+ Структура хранения: 1 таблица с jsonb-колонкой под поля с данными, FK технически отсутствует (используется пара "code записи в таблице" + "дата"). 
+ Версионирование: Исторические данные в текущей таблице. Тип версионирования = Интервал.


Пример. Оба справочника лежат в одной таблице. Секция задаётся `dictionary_code`. Поля, кроме кода и срока, сидят в `data`. Родитель — это `parent_code` той же таблицы и дата: у стали родитель `METAL`, его имя берётся из открытого на 2026-10-20 интервала строки `METAL`.

`dictionary_row`, секции `WallKind` и `WallMaterial`

| dictionary_code | value_code | parent_code | valid_from | valid_to | data |
| --- | --- | --- | --- | --- | --- |
| WallKind | STONE | | 2024-01-01 | | `{"name":"Камень"}` |
| WallKind | WOOD | | 2024-01-01 | | `{"name":"Дерево"}` |
| WallKind | METAL | | 2026-10-20 | | `{"name":"Металл"}` |
| WallMaterial | BRICK | STONE | 2024-01-01 | 2026-10-19 | `{"name":"Кирпич","is_bearing":true,"density":1800}` |
| WallMaterial | BRICK | STONE | 2026-10-20 | | `{"name":"Кирпич керамический","is_bearing":true,"density":1800}` |
| WallMaterial | TIMBER | WOOD | 2024-01-01 | | `{"name":"Брус","is_bearing":false,"density":500}` |
| WallMaterial | STEEL | METAL | 2026-10-20 | | `{"name":"Сталь","is_bearing":true,"density":7850}` |


Особенности:
+ Смысл Jsonb = динамическая структура
+ Нет прямых ссылок. Вместо FK будет код родителя в текущей таблице и дата, на которую надо найти валидное значение кода. 
+ Секционирование для разделения справочников друг от друга на 1 таблице 

Хорошо: 
+ <mark style="background:#90EE90;color:#222">Создание справочника - поддерживается, без SQL</mark>
+ <mark style="background:#90EE90;color:#222">Изменение метаданных - поддерживается, без SQL</mark>
+ <mark style="background:#90EE90;color:#222">Механизм поиска по актуальным и истореческим данным - одинаковый</mark>
+ <mark style="background:#90EE90;color:#222">Размер таблицы - минимальный</mark> (избыточное дублирование при выпуске новой версии)
+ Поиск (без FK) - быстрый
+ Размер таблицы - минимальный (отсутствие избыточного дублирования)

Плохо:
- <mark style="background:#FF4500;color:#222">Изолированный набор данных справочника на каждую версию - нет</mark>
- Валидация полей - нет
- Поиск (с FK) - медленный
