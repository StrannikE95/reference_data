# Подходы к хранению справочников

Три оси ниже не зависят друг от друга. Снимок можно положить и в свои колонки, и в jsonb. Интервал строки можно вести и в отдельной таблице справочника, и в EAV. Оценка исходит из уже зафиксированного контура: PostgreSQL, снаружи хранится код или код с редакцией или дата, декларативной связи из базы домена в базу справочников нет, внутри справочника связи бывают, ломающая смена колонок — это новый справочник, адресный массив целиком сюда не входит.

## 1. Атомарность версионирования

### 1.1. Редакция всего справочника

Новая версия — полная копия списка плюс изменения. `version_id`, «дата с» и «дата по» принадлежат редакции в каталоге. В данных редакции одна секция: все её строки несут один и тот же `version_id`.

Достоинства:

- «Весь список редакции N» — один фильтр по `version_id`. Для снимка это секция, планировщик не читает остальные редакции.
- «Старый контракт видит старый состав» закрывается парой `(value_code, version_id)`. Публикация ничего снаружи не переписывает: старая секция остаётся на старом номере.
- Состав редакции неизменен после публикации. Откатить чтение к прошлому списку — значит назвать номер.
- Связь внутри справочника обычная: `(version_id, код родителя)` ссылается на строку той же редакции.
- Черновик, публикация, закрытие и архив уже описаны на каталоге. Архив — отсоединение секции, каталог редакции остаётся.
- Короткий список копировать дёшево. Кэш редакции — это карта `value_code → строка` одного номера.

Недостатки:

- В длинном списке публикация копирует и неизменившиеся строки. Место и время растут от размера списка, а не от размера правки.
- Две таблицы одного набора публикуются одним номером. Забыли секцию во второй таблице — редакция дырявая.
- Исправить одну опечатку в закрытой редакции нельзя: правка — новая полная редакция.
- Потребитель, который хранит только код и хочет «как сейчас», должен отдельно резолвить активную редакцию. Сама строка номер редакции не выбирает.

Уместно для коротких и средних списков, где важнее простое чтение редакции целиком, чем экономия на копии.

### 1.2. Интервал одной записи

`version_id` редакции справочника нет. У строки есть собственные «дата с» и «дата по». Изменился один элемент — старая строка этого кода закрывается, пишется одна новая. Остальные коды не копируются. Снаружи для зафиксированного чтения хранится дата, не номер редакции.

Достоинства:

- Объём записи равен объёму правки. Длинный перечень с редкими изменениями не плодит полные копии.
- «Что действовало в день D» и «какой сейчас открытый интервал кода» отвечают одним условием по датам строки.
- Мягкое удаление — закрытый интервал без открытого продолжения. Код остаётся в истории.
- Публикация пачки — одна транзакция и общая дата начала у изменённых строк. Отдельный номер на это не нужен.
- Длинный процесс хранит дату старта. По одной дате читаются разные справочники, у которых нет общего счётчика редакций.

Недостатки:

- «Весь список на дату» — не секция, а условие «интервал накрывает дату». Нужен индекс по коду и дате начала. На каждый такой запрос планировщик собирает срез, а не открывает готовую редакцию.
- Закрытый интервал нельзя переписывать. Иначе «на 20.10.2026» завтра означает другой состав. Второе изменение в тот же день требует времени в «дата с», не одной календарной даты: дневная точность сливает два выпуска в один.
- Черновик — это строки, чей интервал ещё не открыт. Правила черновика живут на строках, а не на одной записи каталога.
- Архив «унести редакцию 12» не определён: уносить нечего, история нарезана по кодам. Выкинуть историю старше даты можно, вырезать один выпуск посередине — нет.
- Связь на родителя должна указывать код и попадать в его интервал на ту же дату. Декларативная связь PostgreSQL так не пишется: у родителя несколько строк одного кода. Остаётся проверка при записи либо запрет менять код, на который уже есть ссылки.
- Кэш «весь текущий список» сбрасывается от правки одной строки. Кэш одной редакции по номеру здесь не из чего собрать.

Уместно, когда список большой, правка точечная, а потребителю нужна дата, а не номер выпуска. Ломающую смену колонок этот механизм не покрывает.

### 1.3. Текущая строка и журнал истории

Отдельный приём той же оси. В основной таблице один актуальный ряд на код. Прошлые состояния лежат в `*_history`. Так выглядела идея таблицы `Wall Material History`.

Достоинства:

- Чтение «как сейчас» — обычный поиск по коду, без фильтра по дате и без выбора активной редакции.
- История не мешает индексам актуального списка.
- Объём основной таблицы равен числу живых кодов.

Недостатки:

- Состояние элемента записано в двух местах. Ошибка переноса в журнал оставляет либо дыру, либо два актуальных ряда.
- «Список на дату» склеивает журнал и актуальные строки. Запрос сложнее, чем у интервала в одной таблице.
- Связь и уникальность кода действуют на актуальную таблицу. Историческая строка в ту же связь уже не встаёт.
- Два объекта на каждый справочник: таблица и её журнал. Для набора из нескольких таблиц журналов столько же.

Уместно, если почти все чтения — про текущий список, а история нужна редко и её допустимо держать отдельным хвостом. Для одинаково частых запросов «сейчас» и «на дату» проще одна таблица интервалов.

### 1.4. Манифест редакции без копии строк

Редакция — не секция со всеми строками, а список пар «код → конкретная строка интервала». Неизменённый код в новый манифест не копируется, на него остаётся указатель. Номер редакции при этом есть.

Достоинства:

- Потребитель по-прежнему хранит `(value_code, version_id)`, как у снимка.
- Полный список редакции собирается соединением манифеста со строками. Неизменившиеся строки физически одни.
- Можно издать пустой выпуск «список подтверждён, правок нет»: появляется манифест, строк не добавляется.

Недостатки:

- Появляются два источника правды: интервалы строк и состав манифеста. Их надо писать одной транзакцией.
- «Список редакции N» дороже, чем секция снимка: это соединение, не чтение одной секции.
- На больших выпусках манифест сам становится копией списка кодов. Выигрыш только по телу строки, не по числу ссылок.
- Связи между кодами надо проверять внутри одного манифеста, а не внутри одной секции.

Уместно, только если снаружи обязан остаться номер редакции, а копировать тело длинных строк уже дорого. Если снаружи хранится дата, манифест повторяет то, что дата и так выбирает из интервалов.

## 2. Структура хранения

### 2.1. Своя таблица на справочник

Как сейчас: у простого списка своя таблица, у набора — своя схема и несколько таблиц. Имена и колонки известны базе.

Достоинства:

- Типы, `NOT NULL`, уникальность кода и связь между таблицами набора пишет сама PostgreSQL.
- Запрос страницы, поиск по подписи и проверка списка кодов — обычный SQL по известным колонкам.
- Секционирование по `version_id` ложится на конкретную таблицу. Архив одной редакции не трогает чужие справочники.
- Индекс строится по реальному полю: код, имя, дата, родитель.
- Набор из нескольких таблиц остаётся набором таблиц. Порядок загрузки родителя раньше ребёнка совпадает с внешним ключом.

Недостатки:

- Новый справочник в принятой сейчас схеме — это `CREATE TABLE` в рантайме. На совещании это уже назвали плохой практикой: ошибка в колонках становится объектом базы, а не строкой настройки.
- Число таблиц растёт с числом справочников. Для коротких enum это шумно: отдельная таблица ради десяти строк.
- Общий код чтения не может сказать `SELECT * FROM dictionary`. Он подставляет имя таблицы из паспорта.
- Смена набора колонок у живой таблицы — `ALTER TABLE`. Для снимка это ещё и вопрос, влезает ли новая колонка в старые секции.

Уместно для справочников с собственными колонками, связями и заметным размером. Текущая спецификация стоит на этом варианте.

### 2.2. EAV: сущность, атрибут, значение

Три общие таблицы. Справочник и его элемент — сущности. Поле — строка атрибута. Факт «у кирпича имя такое-то» — строка значения. Схема справочника — набор атрибутов, без `CREATE TABLE`.

Достоинства:

- Новый справочник и новое поле — вставка в каталог, не смена схемы базы.
- Один и тот же SQL читает любой справочник. Динамический состав полей не плодит таблицы.
- Модель старая и предсказуемая: связи между каталогом и значениями — обычные внешние ключи.
- Короткие enum и длинные списки лежат в одной форме. Отдельный зоопарк таблиц не появляется.

Недостатки:

- Одна логическая строка справочника размазана на столько записей, сколько у неё полей. Страница из 100 элементов по 10 полей — это сборка тысячи строк значения.
- Тип значения общий для всех атрибутов. Либо всё строкой, либо набор колонок `value_text`, `value_int`, `value_date`, `value_uuid` с правилом «заполнена ровно одна». Ошибка типа ловится правилом, не типом колонки.
- Уникальность кода, обязательное поле и связь «родитель существует» — проверки при записи. База сама это не держит так, как `PRIMARY KEY (version_id, value_code)` и `FOREIGN KEY`.
- Индекс по «имени» — индекс по строкам одного атрибута, с фильтром `attribute = name`. Поиск по двум полям сразу — самосоединение значений.
- Интервал на элемент умножает ещё и число атрибутов: закрывать приходится каждое поле элемента или хранить версию элемента отдельно и вешать значения на неё. EAV вместе с интервалом легко становится третьей осью сложности.
- Набор из нескольких таблиц в EAV превращается в типы сущностей и связь между ними. Это читается хуже, чем `addr_obj.level_code → object_level`.

Уместно, если справочники короткие, поля часто добавляются, связи между элементами редки, а запросы почти всегда «дай элемент по коду». Для страниц, поиска и связей внутри набора это дорогая модель.

### 2.3. Одна физическая таблица на все справочники, секция на справочник

Общая таблица с колонкой «какой справочник» и `PARTITION BY LIST` по ней. У каждого справочника своя секция. Колонки у всех секций общие: так устроены секции PostgreSQL, разный набор типизированных колонок в разных секциях объявить нельзя. Поэтому на практике тело строки здесь почти всегда jsonb или EAV, а не свой набор колонок.

Достоинства:

- Справочники разведены физически: свой кеш секции, свой tablespace, свой вакуум, чужие строки не попадают в чтение.
- Новый справочник — `CREATE TABLE ... PARTITION OF`, а не новая логическая модель. Код чтения один.
- Выбросить один справочник — отсоединить его секцию, не трогая остальные.

Недостатки:

- Разная форма колонок через секции не выражается. Кто хотел «у стен свои колонки, у ОКТМО свои» в одной родительской таблице, тот возвращается к jsonb или к отдельным таблицам.
- Ключ секции занят кодом справочника. Редакция-снимок хочет второй ключ, `version_id`. Составной LIST по паре (справочник, редакция) плодит секцию на каждую пару и упирается в число секций.
- Внешний ключ между двумя справочниками в этой таблице — связь секции на саму родительскую таблицу. Писать его можно, читать план запроса уже неприятно.
- Смысл секции и смысл редакции начинают спорить за один и тот же механизм `PARTITION BY LIST`.

Уместно как физическая раскладка общей таблицы с одинаковыми колонками, когда справочников много и их полезно развести по дискам. Замену отдельным таблицам с собственными колонками этот приём не даёт.

## 3. Формат полей

### 3.1. Колонка на каждое поле

Как сейчас: `value_code`, `name`, дальше поля справочника своими типами `varchar`, `integer`, `bigint`, `date`, `uuid`.

Достоинства:

- Тип, длина и обязательность держит таблица.
- Индекс, сортировка, поиск по подстроке и связь строятся по колонке.
- Страница значений читается без разбора документа.
- Выгрузка в файл и проверка колонок совпадают со схемой таблицы один в один.

Недостатки:

- Новое поле в живом справочнике — изменение таблицы. Для снимка колонка появляется и в старых секциях.
- Пустые поля короткого справочника всё равно присутствуют в строке. Для десяти колонок это незаметно, для сотни редко заполненных — ширина строки.
- Общий код не знает колонки заранее: он читает их из паспорта и подставляет в SQL.

Уместно, пока у справочника устойчивый короткий набор полей и по ним ищут, сортируют и строят связи.

### 3.2. Все значимые поля в jsonb

В таблице остаются только служебные колонки: справочник, код, при снимке ещё `version_id`, при интервале — даты. Имя, родитель и прочие поля лежат в `jsonb`.

Достоинства:

- Новый набор полей не меняет таблицу. В каталог пишется схема документа, строки кладутся в ту же таблицу.
- Динамические справочники и редкие атрибуты не раздувают `ALTER TABLE`.
- PostgreSQL индексирует jsonb: GIN по документу, btree по выражению `data->>'name'`, если по полю реально ищут.
- Один формат строки для всех справочников упрощает общий загрузчик.

Недостатки:

- Внешний ключ по пути внутри jsonb объявить нельзя. Связь «уровень адресного объекта» потребует сгенерированную колонку `level_code GENERATED ALWAYS AS (data->>'level_code') STORED` и уже по ней ключ. Иначе связь — проверка в коде загрузки.
- Обязательность и тип поля схема базы не держит. Их держит проверка JSON при записи. Ошибка в документе может попасть в таблицу, если проверку обошли.
- Поиск по подписи и сортировка страницы идут по выражению, а не по колонке. Индекс на каждое искомое поле надо завести отдельно.
- Сравнение «строка редакции 4 и строка редакции 5» и выгрузка колонок в файл требуют разбора документа.
- Сгенерированные колонки на каждое поле, по которому ищут или ссылаются, постепенно повторяют обычные колонки. jsonb остаётся у действительно редких атрибутов.

Уместно, когда набор полей разный и часто меняется, а ищут почти всегда по коду. Как только по полям нужны связи и отчёты, jsonb обрастает служебными колонками.

### 3.3. Колонки ключа и jsonb для остального

Код, подпись, родитель и даты — обычные колонки. Редкие и необязательные поля — один `jsonb`.

Достоинства:

- Поиск, уникальность и связь остаются на настоящих колонках.
- Новое необязательное поле не меняет таблицу.
- Строка не раздувается десятками пустых колонок.
- В выгрузке устойчивые колонки читаются как таблица, хвост уходит отдельным объектом.

Недостатки:

- Два места, где лежит смысл строки. Запрос «найди по редкому полю» снова требует выражение по jsonb и отдельный индекс.
- Правило «поле либо колонка, либо ключ в jsonb» надо держать в паспорте. Одно и то же имя в обоих местах даёт тихий разъезд.
- Связь по полю из jsonb упирается в ту же сгенерированную колонку, что и чистый jsonb.

Уместно, если у всех справочников один и тот же костяк (код, подпись, может быть родитель), а остальное различается и по нему почти не ищут.

## 4. Что с чем стыкуется

Рабочие сочетания:

- Снимок, своя таблица, колонки. Текущая спецификация. Лучшее чтение редакции, настоящие связи, понятный архив. Цена — копия списка и `CREATE TABLE`.
- Интервал строки, своя таблица, колонки. Точечные правки длинного списка без номера редакции. Связь между строками одного справочника уже не внешний ключ, а проверка по дате.
- Общая таблица с jsonb и секция на справочник. Много простых справочников без связей между полями, без своей таблицы на каждый. Новый справочник не описывает колонки базе.
- EAV. Много коротких списков, схема которых ещё плавает, запросы точечные. Страницы и связи быстро становятся дороже самих данных.

Сочетания, которые растут в монстра:

- EAV и интервал строки вместе. На каждое поле элемента появляется свой интервал, либо приходится вводить версию элемента и вешать на неё значения. Это уже третья модель поверх двух.
- Снимок и jsonb без сгенерированных колонок, если между таблицами набора есть связи. Связь либо живёт в коде загрузки, либо jsonb всё равно разрезают на колонки.
- Редакция-снимок и секция по справочнику в одной и той же таблице. Оба хотят `PARTITION BY LIST` под свой ключ.
- Манифест редакции плюс EAV. Состав выпуска, элемент и каждое его поле — три уровня косвенности на один код.

Отдельно от этих осей остаётся адресный контур на сотни гигабайт. Ему нужны свой поисковый индекс и свои таблицы. Ни снимок, ни интервал, ни EAV это хранение не заменяют.
