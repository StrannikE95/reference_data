# Постановка: интеграционный модуль

Модуль живёт в отдельной подсистеме. Справочники его не разбирают: он принимает запрос на данные, читает уже скачанный файл и публикует JSON в Kafka. SQL из этого JSON собирает `Постановка. модуль импорта.md`.

Запрос приходит двумя путями, тело одно.

- UI администратора справочников вызывает метод модуля.
- То же тело приходит сообщением Kafka.

```json
{
  "loadId": "6f1c0a2e-7b14-4d2a-9c31-0a6e5d8b41f2",
  "sourceCode": "ass-building",
  "filePath": "C:\\inbox\\dAssBuilding_v04.xsd",
  "product": "metadata"
}
```

`product` равен `metadata` или `data`. `loadId` связывает все сообщения одного прогона. `filePath` существует и лежит внутри каталога `Import:Root`, иначе запрос отвергается с `path_not_allowed`.

На выходе две структуры и только они.

## Метаданные

Описание таблиц, которые модуль увидел в файле: имя, поля, типы, ключ, связи. Паспорта справочника, `version_id` и секции здесь нет — это поля модуля справочников, их добавляет импорт.

Топик: `dictionary.integration.metadata`.

```json
{
  "loadId": "6f1c0a2e-7b14-4d2a-9c31-0a6e5d8b41f2",
  "sourceCode": "ass-building",
  "sourceFile": "dAssBuilding_v04.xsd",
  "tables": [
    {
      "name": "ass_building",
      "columns": [
        { "name": "value_code", "type": "string", "length": 12, "nullable": false },
        { "name": "name", "type": "string", "length": 500, "nullable": false }
      ],
      "primaryKey": ["value_code"],
      "foreignKeys": []
    }
  ]
}
```

## Данные

Содержимое тех же таблиц. Одно сообщение — пачка строк одной таблицы. У большого файла сообщений несколько; у них общий `loadId`.

Топик: `dictionary.integration.data`.

```json
{
  "loadId": "6f1c0a2e-7b14-4d2a-9c31-0a6e5d8b41f2",
  "sourceCode": "ass-building",
  "sourceFile": "dAssBuilding_v05.xsd",
  "part": 1,
  "last": true,
  "tables": [
    {
      "name": "ass_building",
      "rows": [
        { "value_code": "204001000000", "name": "Нежилое" },
        { "value_code": "204002000000", "name": "Жилой дом" }
      ]
    }
  ]
}
```

`part` начинается с 1. `last: true` стоит на последнем сообщении прогона. Пачка — до 1000 строк. Порядок строк в сообщениях — порядок, в котором их можно вставлять: родитель раньше ребёнка.

Поля строки называются так же, как колонки метаданных этого `sourceCode`. Пустое значение, которое по правилам источника отсутствует, пишется `null`.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "dictionary.integration.data",
  "type": "object",
  "additionalProperties": false,
  "required": ["loadId", "sourceCode", "sourceFile", "part", "last", "tables"],
  "properties": {
    "loadId": { "type": "string", "format": "uuid" },
    "sourceCode": {
      "enum": ["ass-building", "wall-material", "oktmo", "gar"]
    },
    "sourceFile": { "type": "string", "minLength": 1 },
    "part": { "type": "integer", "minimum": 1 },
    "last": { "type": "boolean" },
    "skippedLevel": { "type": "integer", "minimum": 0 },
    "tables": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["name", "rows"],
        "properties": {
          "name": { "type": "string", "minLength": 1 },
          "rows": {
            "type": "array",
            "maxItems": 1000,
            "items": { "type": "object" }
          }
        }
      }
    }
  }
}
```

Ошибка разбора публикует в топик `dictionary.integration.result` одно сообщение с тем же `loadId` и кодом ошибки. Сообщения метаданных и данных этого прогона не отправляются. Повтор кода в одном прогоне — `duplicate_code`. Пустой результат — `empty`.

## 1. Назначение здания

Файл `dAssBuilding_v04.xsd` берётся из архива на странице [XML-схемы](https://rosreestr.gov.ru/activity/okazanie-gosudarstvennykh-uslug/vedenie-egrn/xml-skhemy/). Отдельного URL у одного XSD нет. Читается короткий классификатор, не схема технического плана `TP_v07.xsd`.

Фрагмент источника:

```xml
<xs:simpleType name="dAssBuilding">
  <xs:restriction base="xs:string">
    <xs:enumeration value="204001000000">
      <xs:annotation>
        <xs:documentation>Нежилое</xs:documentation>
      </xs:annotation>
    </xs:enumeration>
  </xs:restriction>
</xs:simpleType>
```

Чтение — `XDocument`. Элементы ищутся по локальному имени, префикс `xs` или `xsd` не важен. Берётся один `simpleType` с `name="dAssBuilding"`. Нет такого или их больше одного — `type_not_found`. В `TP_v07.xsd` этого типа нет, там только ссылка, поэтому схема технического плана останавливается здесь.

Внутри типа берутся прямые `enumeration` из `restriction`. `value` — `value_code`, текст первого `documentation` — `name`. Пробелы по краям срезаются. Код — ровно 12 цифр. Имя не пустое и не длиннее 500 символов. Нет `documentation` — `name_not_in_xsd`, в теле список кодов без названия. Имя из PDF и HTML не подставляется.

`product: metadata` публикует таблицу `ass_building` из примера выше. Строк в этом сообщении нет.

`product: data` публикует пары в `rows`. Для известного состава это четыре строки: `204001000000` Нежилое, `204002000000` Жилой дом, `204003000000` Многоквартирный дом, `204004000000` Жилое строение. В сообщение попадает фактический состав файла. Следующий выпуск — файл вида `dAssBuilding_v05.xsd` с той же страницы, тот же разбор.

## 2. Материал наружных стен

Файл `dWall_v02.xsd` лежит в том же архиве: [XML-схемы](https://rosreestr.gov.ru/activity/okazanie-gosudarstvennykh-uslug/vedenie-egrn/xml-skhemy/). Разбор `enumeration` тот же, имя типа — `dWall`.

После сбора пар считается родитель. Код делится на четыре группы по три цифры. Обнуляется самая правая ненулевая группа; если код есть в этом файле, это родитель; иначе обнуляется следующая группа влево. Группа `000` пропускается. Слева групп не осталось — родителя нет, в JSON `null`.

Проверка: у `061001001001` родитель `061001001000`, у того `061001000000`, у `061001000000` родителя нет. Код, которого в файле нет, ошибкой не считается: берётся следующая группа. Код сошёлся сам на себя — `parent_cycle`.

Метаданные:

```json
{
  "name": "wall_material",
  "columns": [
    { "name": "value_code", "type": "string", "length": 12, "nullable": false },
    { "name": "name", "type": "string", "length": 500, "nullable": false },
    { "name": "parent_code", "type": "string", "length": 12, "nullable": true }
  ],
  "primaryKey": ["value_code"],
  "foreignKeys": [
    { "columns": ["parent_code"], "references": { "table": "wall_material", "columns": ["value_code"] } }
  ]
}
```

В данных родитель стоит в более ранней строке, чем ребёнок. Сначала коды без родителя, затем те, чей родитель уже записан. Неразобранный остаток — `parent_cycle`. Новый выпуск — `dWall_v03.xsd` из следующего архива той же страницы.

## 3. ОКТМО

Файл: [https://classifikators.ru/assets/downloads/oktmo/oktmo.csv](https://classifikators.ru/assets/downloads/oktmo/oktmo.csv). CSV без заголовка, разделитель `;`, поля в двойных кавычках. Кавычка внутри поля удваивается.

```text
"01";"512";"000";"101";"8";"2";"с Залесово";;;"493";"3";12.08.2021;01.01.2022
```

| Номер | Поле JSON | Пример |
|---|---|---|
| 0 | часть кода, 2 цифры | `01` |
| 1 | часть кода, 3 цифры | `512` |
| 2 | часть кода, 3 цифры | `000` |
| 3 | часть кода, 3 цифры | `101` |
| 4 | контрольное число, в код не входит | `8` |
| 5 | `section`: `1` или `2` | `2` |
| 6 | `name` | `с Залесово` |
| 7 | центр, в JSON не пишется | пусто |
| 8 | описание, в JSON не пишется | пусто |
| 9 | `change_number` | `493` |
| 10 | тип изменения, в JSON не пишется | `3` |
| 11 | дата принятия, в JSON не пишется | `12.08.2021` |
| 12 | `introduced_on` | `01.01.2022` |

`value_code` — склейка колонок 0–3, 11 цифр: `01512000101`. Один и тот же код бывает в двух разделах: это две строки. Ключ — `value_code` и `section`.

Чтение — `StreamReader`. Сначала UTF-8. Если в первых 20 наименованиях есть `U+FFFD`, файл читается заново как windows-1251. Кавычки разбираются вручную: разделитель внутри кавычек в наименованиях встречается. Строка короче 13 колонок — `bad_csv_row` и номер строки. Колонки 0–3 не той длины — `bad_code`. Дата не `dd.MM.yyyy` — `bad_date`. Пустое имя — `empty_name`. В JSON дата уже `yyyy-MM-dd`.

Родитель ищется внутри того же `section`. От 11-значного кода: последние 3 цифры не `000` — родитель с последними тремя нулями; иначе цифры 6–8 не `000` — нули в позициях 6–11; иначе цифры 3–5 не `000` — нули в позициях 3–11; иначе родителя нет. Ссылка пишется, только если строка с таким кодом и тем же разделом есть в файле.

Метаданные — таблица `oktmo`. Колонки: `value_code` string 11, `section` string 1, `name` string 500, `parent_code` string 11 nullable, `change_number` string 10, `introduced_on` date. Ключ — `value_code`, `section`. Связь: `(parent_code, section)` → `oktmo (value_code, section)`.

Данные идут пачками по 1000 строк, родитель раньше ребёнка. Новый срез лежит на карточке [https://rosstat.gov.ru/opendata/7708234640-oktmo](https://rosstat.gov.ru/opendata/7708234640-oktmo), файл `data-ГГГГММДД-structure-....csv`. Дату из имени метод не читает.

## 4. ГАР

Структура: [https://data.nalog.ru/opendata/7707329152-fias/structure-12032021.zip](https://data.nalog.ru/opendata/7707329152-fias/structure-12032021.zip).

Полный срез: [https://fias.nalog.ru/opendata/7707329152-fias/data-16102026-structure-20191024.zip](https://fias.nalog.ru/opendata/7707329152-fias/data-16102026-structure-20191024.zip). Предыдущие срезы: [13.10.2026](https://fias.nalog.ru/opendata/7707329152-fias/data-13102026-structure-20191024.zip), [09.10.2026](https://fias.nalog.ru/opendata/7707329152-fias/data-09102026-structure-20191024.zip). Полный ZIP около 57 ГБ, на диск целиком не распаковывается.

В прогон входят два файла выгрузки. Остальные XML архива пропускаются.

- `AS_OBJECT_LEVELS_*.XML` — уровни;
- `AS_ADDR_OBJ_*.XML` — адресные объекты.

Имя может содержать дату и номер части: `AS_ADDR_OBJ_20261016_01.XML`. Отбор по началу имени без учёта регистра. Элемент записи — `OBJECT`, поля — атрибуты.

```xml
<OBJECT ID="723807" OBJECTID="597041" OBJECTGUID="..." NAME="Тверская"
        TYPENAME="ул" LEVEL="8" ISACTUAL="1" ISACTIVE="1"
        STARTDATE="2014-01-01" ENDDATE="2079-06-06"/>
```

```xml
<OBJECT LEVEL="8" NAME="Элемент улично-дорожной сети" SHORTNAME="Улица" ISACTIVE="1"/>
```

Чтение данных — `XmlReader`, `IgnoreWhitespace = true`, `DtdProcessing = Prohibit`. `XmlDocument` и `XDocument` на `AS_ADDR_OBJ` не используются. Атрибуты `OBJECT` читаются, элемент сбрасывается.

В адресные строки попадает запись с `ISACTUAL="1"` и `ISACTIVE="1"`. Уровни — строки с `ISACTIVE="1"`. `object_id` берётся из `OBJECTID`, не из `ID`.

Метаданные читают маленький ZIP структуры, `product: metadata`, `filePath` — путь к `structure-12032021.zip`. В архиве ищутся XSD по началу имени `AS_OBJECT_LEVELS` и `AS_ADDR_OBJ`. Нет любого — `xsd_not_found`. Атрибуты из примеров выше должны быть в своём XSD как `attribute` с тем же `name`. Нет атрибута — `xsd_attribute_missing`. Состав колонок при этом фиксирован здесь, из XSD он не выводится: XSD подтверждает, что архив — тот выпуск.

Две таблицы:

| Таблица | Колонки | Ключ | Связь |
|---|---|---|---|
| `object_level` | `level_code` string 10, `name` string 250, `short_name` string 50 | `level_code` | |
| `addr_obj` | `object_id` bigint, `object_guid` uuid, `name` string 250, `type_name` string 50, `level_code` string 10, `start_date` date, `end_date` date | `object_id` | `level_code` → `object_level.level_code` |

Данные читают полный ZIP. Сначала все `AS_OBJECT_LEVELS`, их строки публикуются в таблицу `object_level`. Затем части `AS_ADDR_OBJ` пачками по 1000 в таблицу `addr_obj`. `LEVEL`, которого нет среди опубликованных уровней, в пачку не входит; счётчик `skippedLevel` пишется в последнее сообщение и ошибкой не является. Повтор `OBJECTID` среди отобранных — `duplicate_code`, прогон закрывается сообщением в `dictionary.integration.result`. Атрибут отсутствует или не того вида — `bad_gar_row`, имя файла и `OBJECTID` в теле.

Таб и перевод строки в текстовом поле заменяются пробелом до публикации, чтобы пачка оставалась одной JSON-строкой на запись.
