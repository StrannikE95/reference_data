# Модуль справочников: контракт администратора

Команду принимает модуль. Полномочие владельца проверяет подсистема ИБ. Кэш этим контрактом не меняется: событие публикации обрабатывает сервис чтения.

Содержимое таблиц в JSON не передаётся. Профиль и версия собираются из файлов в объектном хранилище модуля. Клиент записывает файл по выданной ссылке, частями, и может продолжить оборванную запись. Дата в запросе — календарный день `YYYY-MM-DD`. Повтор чтения каталога не меняет данные.

## 1. Просмотр каталога

### 1.1. Список паспортов

`GET /admin/dictionaries`

Параметры запроса: `limit` и `cursor`.
Страница упорядочена по `dictionary_code`. `limit` допустим от 1 до 1000. Без `limit` модуль отдаёт не больше 1000 строк. `cursor` непрозрачен. Конец списка — пустой `next_cursor`.

```json
{
  "items": [
    {
      "dictionary_id": "6b1f3c2a-1d4e-4a7b-9c31-0a5e8f2b7d10",
      "dictionary_code": "WallMaterial",
      "dictionary_name": "Материал стен",
      "owner": "Имущество",
      "source": "Ведомственный перечень",
      "status": "active",
      "table_name": "wall_material",
      "schema_name": null
    }
  ],
  "next_cursor": null
}
```
	
	`table_name` или `schema_name` — размещение, зафиксированное при регистрации. Заполнено одно из двух. Строк версий в этом ответе нет. Незавершённая регистрация в этот список не входит.
	
	### 1.2. Паспорт и версии
	
	`GET /admin/dictionaries/{dictionary_code}`
	
	Ответ — паспорт и все строки `dictionary_version` этого справочника, по возрастанию `version_id`. Пока версии нет, `versions` пуст. У каждой версии те же `table_name` и `schema_name`, что у паспорта.

```json
{
  "dictionary_id": "6b1f3c2a-1d4e-4a7b-9c31-0a5e8f2b7d10",
  "dictionary_code": "WallMaterial",
  "dictionary_name": "Материал стен",
  "owner": "Имущество",
  "source": "Ведомственный перечень",
  "status": "active",
  "table_name": "wall_material",
  "schema_name": null,
  "versions": [
    {
      "dictionary_version_id": "c2a91e40-7b55-4d1a-8e66-15f0c9a4b812",
      "version_id": 1,
      "status": "closed",
      "valid_from": "2024-01-01",
      "valid_to": "2026-10-19",
      "table_name": "wall_material",
      "schema_name": null
    },
    {
      "dictionary_version_id": "e84b0d17-2f6c-4c9a-b331-90ad6e5f4412",
      "version_id": 2,
      "status": "active",
      "valid_from": "2026-10-20",
      "valid_to": null,
      "table_name": "wall_material",
      "schema_name": null
    }
  ]
}
```

Строки значений, секции и кэш в ответ не входят.

## 2. Файлы набора

Файл принадлежит открытой регистрации или черновику версии. Пачка — от 1 до 100 описаний файлов в одном запросе. Следующий запрос дополняет тот же набор.
Один и тот же `name` в наборе один. Повторный запрос с уже существующим именем заменяет файл в состоянии `uploading`, `valid` или `invalid`. Файл в состоянии `loaded` так не заменяется.

| `state` | Что означает |
|---|---|
| `uploading` | Ссылка выдана, запись файла не подтверждена |
| `invalid` | Файл разобран и отклонён. Заполнено `error` |
| `valid` | Файл принят и ждёт завершения |
| `loading` | Идёт заливка этого файла в секцию черновика |
| `loaded` | Строки файла уже в секции черновика |
У регистрации бывают только `uploading`, `invalid` и `valid`. `loading` и `loaded` появляются у черновика версии.

```json
{
  "file_id": "91c0e2b4-6a18-4f0d-9b77-3e5a1c8d4420",
  "name": "wall_material.sql",
  "size": 240,
  "state": "invalid",
  "error": "sql_not_allowed"
}
```

Пока `error` нет, поле пустое.

### 2.1. Начать запись пачки

`POST /admin/registrations/{registration_id}/files`
`POST /admin/dictionaries/{dictionary_code}/draft/files`

```json
{
  "files": [
    { "name": "wall_material.sql", "size": 240 }
  ]
}
```

Ответ — описания с ссылкой на запись. `upload_url` принимает содержимое файла и больше никуда не используется.

```json
{
  "files": [
    {
      "file_id": "91c0e2b4-6a18-4f0d-9b77-3e5a1c8d4420",
      "name": "wall_material.sql",
      "size": 240,
      "state": "uploading",
      "error": null,
      "upload_url": "https://storage.example/upload/91c0e2b4"
    }
  ]
}
```

### 2.2. Подтвердить запись

`POST /admin/registrations/{registration_id}/files/{file_id}/complete`
`POST /admin/dictionaries/{dictionary_code}/draft/files/{file_id}/complete`

Модуль проверяет дописанный файл и возвращает его описание. Для профиля файл должен быть созданием таблиц в исходном виде, без `version_id`: без удаления, без правки каталога и без чужой схемы. Для версии файл должен заполнять исходную таблицу профиля. Отклонённый файл остаётся в наборе со состоянием `invalid`.

Недописанный файл получает `upload_incomplete`.

### 2.3. Удалить файл

`DELETE /admin/registrations/{registration_id}/files/{file_id}`
`DELETE /admin/dictionaries/{dictionary_code}/draft/files/{file_id}`

Снимает файл с набора. Ответ без тела. Удаление файла в состоянии `loaded` дополнительно очищает секцию черновика только той таблицы, которую файл заполнял. Остальные таблицы черновика не меняются. Файл в состоянии `loading` не удаляется.

## 3. Добавление профиля

### 3.1. Открыть регистрацию

`POST /admin/registrations`

Тело — поля паспорта. Паспорт в каталог ещё не пишется, таблицы не создаются.

```json
{
  "dictionary_code": "WallMaterial",
  "dictionary_name": "Материал стен",
  "owner": "Имущество",
  "source": "Ведомственный перечень"
}
```

```json
{
  "registration_id": "a17d5e90-4c22-4b8e-8f01-6d9a2b3c4401",
  "dictionary_code": "WallMaterial",
  "dictionary_name": "Материал стен",
  "owner": "Имущество",
  "source": "Ведомственный перечень",
  "files": []
}
```

Пока регистрация открыта, тот же `dictionary_code` нельзя занять второй регистрацией или паспортом.

### 3.2. Прочитать регистрацию

`GET /admin/registrations/{registration_id}`

Ответ тот же, что при открытии, со текущим списком файлов.

### 3.3. Отменить регистрацию

`DELETE /admin/registrations/{registration_id}`

Удаляет регистрацию и её файлы. Паспорт не создаётся. Ответ без тела.

### 3.4. Завершить регистрацию

`POST /admin/registrations/{registration_id}/commit`

Завершение доступно, когда в наборе есть хотя бы один файл, каждый файл в состоянии `valid` и внешний ключ ссылается только на таблицу этого набора. Модуль сохраняет файлы как профиль, добавляет `version_id` в первичный ключ, уникальность и внешние ключи, создаёт родительские таблицы без секций и пишет паспорт со статусом `active`. Одна таблица даёт `table_name`, несколько — `schema_name`. Имя дальше не меняется.

Ответ — паспорт без версий. Строка `dictionary_version` не создаётся. Регистрация после ответа закрыта.

```json
{
  "dictionary_id": "6b1f3c2a-1d4e-4a7b-9c31-0a5e8f2b7d10",
  "dictionary_code": "WallMaterial",
  "dictionary_name": "Материал стен",
  "owner": "Имущество",
  "source": "Ведомственный перечень",
  "status": "active",
  "table_name": "wall_material",
  "schema_name": null,
  "versions": []
}
```

## 4. Добавление версии

### 4.1. Открыть черновик

`POST /admin/dictionaries/{dictionary_code}/draft`

Публикация этим запросом не выполняется. Если черновика нет, модуль заводит его: `version_id` на единицу больше максимального номера этого справочника и пустые секции во всех таблицах профиля. Если черновик уже есть, возвращается он. Второй черновик не создаётся.

```json
{
  "delivery": "full"
}
```

| `delivery`  | Что делает завершение заливки                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `full`      | Для каждого принятого файла заново заполняет секцию его таблицы                                                                                  |
| `increment` | Копирует строки действующей версии в черновик и применяет дельту. Принимается, только когда профиль описывает новую строку, изменение и удаление |

Пока профиль не описывает дельту, `increment` получает `increment_not_supported` и черновик не создаёт.

```json
{
  "dictionary_code": "WallMaterial",
  "version_id": 3,
  "version_status": "draft",
  "delivery": "full",
  "files": []
}
```

### 4.2. Прочитать черновик

`GET /admin/dictionaries/{dictionary_code}/draft`

Ответ тот же, что при открытии, со текущим списком файлов. Этим запросом экран видит переход `valid` → `loading` → `loaded`.

### 4.3. Завершить заливку

`POST /admin/dictionaries/{dictionary_code}/draft/apply`

В заливку идут файлы в состоянии `valid`. Для версии набор полон, когда на каждую таблицу профиля есть файл. Модуль обрабатывает файл за файлом и фиксирует каждую таблицу отдельно. Сначала копируется родитель, потом зависимая таблица. Ошибка проверки одной таблицы переводит её файл в `invalid` и не откатывает таблицы, которые уже `loaded`.

Проверки строк: простой список не пуст, `value_code` уникален внутри номера, внешние ключи сходятся внутри этого номера, секция таблицы есть.

Ответ — черновик. Файлы, взятые в работу, уже в состоянии `loading` либо, если таблица успела зафиксироваться, `loaded`. Сервис чтения эти строки не отдаёт.

Повторное завершение обрабатывает только файлы, которые снова в состоянии `valid`.

### 4.4. Отмена черновика

`DELETE /admin/dictionaries/{dictionary_code}/draft`

Удаляет секции черновика, его файлы и строку `dictionary_version`. События нет. Номер отменённого черновика может получить следующий. Ответ без тела. Черновик с файлом в состоянии `loading` не отменяется.

## 5. Активация версии

`POST /admin/dictionaries/{dictionary_code}/draft/publish`

Переходы `draft → active` и прежний `active → closed` выполняются одной командой. Тело — `valid_from`.

```json
{
  "valid_from": "2026-11-01"
}
```

Модуль блокирует паспорт, закрывает прежнюю действующую версию с `valid_to` на день раньше `valid_from` и в той же транзакции пишет событие: код справочника, новый `version_id`, `valid_from`, номер прежней действующей версии. Откат транзакции откатывает и событие. Черновик и его секции остаются. Закрыть действующую версию отдельной командой нельзя.

Публикация проходит, когда версия — черновик этого справочника, паспорт в статусе `active`, каждый файл черновика в состоянии `loaded`, простой список не пуст, у набора секции этого номера есть во всех таблицах схемы, `valid_from` заполнен, не позже дня публикации и, если действующая версия есть, строго позже её `valid_from`.

```json
{
  "dictionary_code": "WallMaterial",
  "version_id": 3,
  "version_status": "active",
  "valid_from": "2026-11-01",
  "valid_to": null,
  "closed_version_id": 2,
  "closed_valid_to": "2026-10-31"
}
```

У первой публикации `closed_version_id` и `closed_valid_to` пусты.

## 6. Ошибки

Ошибка команды — не пустой список версий и не файл в состоянии `invalid`. Такой файл остаётся в наборе и виден при чтении регистрации или черновика.

| Ситуация | `error` | HTTP |
|---|---|---|
| Нет паспорта с таким кодом | `dictionary_not_found` | 404 |
| Нет регистрации с таким номером | `registration_not_found` | 404 |
| Нет файла с таким номером | `file_not_found` | 404 |
| Паспорт или открытая регистрация уже есть с таким `dictionary_code` | `dictionary_already_exists` | 409 |
| Паспорт в статусе `inactive`, а запрошены черновик, заливка или публикация | `dictionary_inactive` | 409 |
| Нет черновика, а запрошены его чтение, файлы, заливка, отмена или публикация | `draft_not_found` | 404 |
| Повторное имя указывает на файл в состоянии `loaded` | `file_loaded` | 409 |
| Удаление или отмена запрошены, пока файл в состоянии `loading` | `file_loading` | 409 |
| `delivery = increment`, а профиль не описывает дельту | `increment_not_supported` | 400 |
| В завершении есть файл не в состоянии `valid`, набор пуст или для версии не хватает файла таблицы профиля | `set_not_ready` | 409 |
| `valid_from` пуст, позже дня публикации или не позже `valid_from` действующей версии | `invalid_valid_from` | 400 |
| `limit` вне 1…1000, неразборчивый `cursor`, пустые поля паспорта, пустое имя файла, `size` меньше 1, в пачке не от 1 до 100 файлов, два одинаковых имени в одной пачке, `delivery` не `full` и не `increment` | `invalid_request` | 400 |

`set_not_ready` перечисляет, чего не хватает:

```json
{
  "error": "set_not_ready",
  "dictionary_code": "Address",
  "missing_tables": ["addr_house"]
}
```

Код в поле `error` файла — один из `sql_not_allowed`, `invalid_sql`, `upload_incomplete`, `unexpected_table`, `empty`, `duplicate_value_code`, `foreign_key`, `partition_missing`.

## 7. Пример

`POST /admin/registrations` открывает регистрацию `WallMaterial`. Пачка из одного `wall_material.sql` после `complete` получает `valid`. `POST .../commit` создаёт родительскую таблицу и паспорт без версий.

`POST .../WallMaterial/draft` с `delivery = full` создаёт версию 1 и пустую секцию. Файл заполнения после `complete` получает `valid`, после `apply` — `loaded`. `DELETE .../draft` снимает версию вместе с файлом.

Повторное открытие черновика снова получает номер 1. `POST .../draft/publish` с `valid_from = 2024-01-01` переводит её в `active`. `closed_version_id` пуст.

Следующий черновик создаёт версию 2. Публикация с `valid_from = 2026-10-20` переводит её в `active`, версии 1 ставит `closed` и `valid_to = 2026-10-19`.

Открытие черновика с `delivery = increment` возвращает `increment_not_supported`: профиль материала стен дельту не описывает. Публикация с `valid_from = 2026-10-20` при уже действующей версии с той же даты возвращает `invalid_valid_from`.
