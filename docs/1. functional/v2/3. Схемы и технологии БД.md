# Схемы и технологии БД (v2)

Описание хранения справочников в PostgreSQL: каталог, версии, таблицы данных, секционирование, архивация и генерация SQL-скриптов. Схема соответствует `Справочники 2.drawio` и контрактам API v2. Одно техническое дополнение: в `dictionary` добавлен `JSON_metadata`, чтобы хранить описание полей до появления первой версии.

## 1. Технологии

| Слой | Технология |
|---|---|
| СУБД | PostgreSQL 17 |
| Драйвер | Npgsql |
| Доступ к каталогу | Dapper |
| Выполнение DDL/DML | Npgsql, SQL-файл целиком |
| Формат метаданных | JSON, хранится как `varchar` |
| Секционирование | `PARTITION BY LIST (version_id)` |
| Архивация | `ALTER TABLE ... DETACH PARTITION` |
| Файлы SQL | локальный диск, каталоги `db/sql-schema` и `db/sql-data` |
| Миграции | SQL-файлы как артефакты, без ORM и migration framework |
| Контур | Dev, один экземпляр PostgreSQL |

Особенности:

- Каждый справочник — отдельная физическая таблица.
- Общими являются только паспорт справочника и строки версий.
- Строки значений в общую таблицу не складываются.
- Одна версия — одна секция физической таблицы.
- SQL-файл сначала пишется на диск, затем выполняется.
- Ошибка выполнения не удаляет SQL-файл: он остаётся для диагностики.
- `JSON_metadata` хранится текстом; JSON проверяется приложением при записи.

## 2. Каталог

### 2.1. `dictionary`

```sql
CREATE TABLE dictionary (
    dictionary_id   uuid         PRIMARY KEY,
    dictionary_code varchar(63)  NOT NULL,
    dictionary_name varchar(200) NOT NULL,
    owner           varchar(200) NULL,
    source          varchar(200) NULL,
    status          varchar(16)  NOT NULL DEFAULT 'active',
    JSON_metadata   varchar      NOT NULL,
    CONSTRAINT dictionary_status_check
        CHECK (status IN ('active', 'inactive'))
);

CREATE UNIQUE INDEX ux_dictionary_code
    ON dictionary (lower(dictionary_code));
```

Назначение полей:

| Поле | Описание |
|---|---|
| `dictionary_id` | Внутренний идентификатор |
| `dictionary_code` | Устойчивый код, уникален без учёта регистра |
| `dictionary_name` | Название для человека |
| `owner` | Предметный владелец; в v2 необязателен |
| `source` | Источник состава; в v2 необязателен |
| `status` | `active` или `inactive` |
| `JSON_metadata` | Текущее описание полей справочника |

`JSON_metadata` в паспорте нужен до появления первой версии: форма создаёт поля, а версии ещё нет. В строке версии хранится снимок этого описания.

`owner` и `source` в v2 не заполняются формой. Они оставлены в схеме и API как необязательные.

### 2.2. `dictionary_version`

```sql
CREATE TABLE dictionary_version (
    dictionary_version_id uuid        PRIMARY KEY,
    dictionary_id         uuid        NOT NULL
        REFERENCES dictionary (dictionary_id),
    version_id            integer     NOT NULL,
    valid_from            date        NULL,
    valid_to              date        NULL,
    status                varchar(16) NOT NULL,
    JSON_metadata         varchar     NOT NULL,
    table_name            varchar(63) NULL,
    schema_name           varchar(63) NULL,
    CONSTRAINT dictionary_version_pk
        UNIQUE (dictionary_id, version_id),
    CONSTRAINT dictionary_version_status_check
        CHECK (status IN ('draft', 'active', 'closed')),
    CONSTRAINT dictionary_version_valid_from_check
        CHECK (valid_from IS NOT NULL OR status = 'draft'),
    CONSTRAINT dictionary_version_valid_to_check
        CHECK (valid_to IS NULL OR valid_from IS NULL OR valid_to >= valid_from),
    CONSTRAINT dictionary_version_active_valid_to_check
        CHECK (status <> 'active' OR valid_to IS NULL),
    CONSTRAINT dictionary_version_closed_valid_to_check
        CHECK (status <> 'closed' OR valid_to IS NOT NULL),
    CONSTRAINT dictionary_version_placement_check
        CHECK ((table_name IS NOT NULL) <> (schema_name IS NOT NULL))
);

CREATE UNIQUE INDEX ux_dictionary_version_active
    ON dictionary_version (dictionary_id)
    WHERE status = 'active';

CREATE UNIQUE INDEX ux_dictionary_version_draft
    ON dictionary_version (dictionary_id)
    WHERE status = 'draft';
```

Назначение полей:

| Поле | Описание |
|---|---|
| `dictionary_version_id` | Внутренний идентификатор версии |
| `dictionary_id` | Ссылка на паспорт |
| `version_id` | Номер версии внутри справочника, начиная с 1 |
| `valid_from` | Дата начала действия; у черновика может быть `null` |
| `valid_to` | Дата окончания; у действующей версии `null` |
| `status` | `draft`, `active` или `closed` |
| `JSON_metadata` | Снимок описания полей на момент версии |
| `table_name` | Имя таблицы простого списка |
| `schema_name` | Имя схемы набора таблиц; в v2 не используется |

Правила:

- У справочника не больше одной действующей версии.
- У справочника не больше одного черновика.
- `valid_to` закрытой версии — день перед `valid_from` следующей действующей версии.
- `version_id` не сквозной между справочниками.
- `version_id` в строках данных не связан внешним ключом с каталогом.
- `archived` не хранится: признак вычисляется по наличию секции.

## 3. Описание полей

`JSON_metadata` — канонический JSON:

```json
{
  "dictionary_code": "WallMaterial",
  "table_name": "wall_material",
  "value_code": {
    "length": 64
  },
  "name": {
    "length": 500
  },
  "fields": [
    {
      "code": "parent_code",
      "name": "Родительский код",
      "type": "string",
      "length": 500,
      "nullable": true
    }
  ]
}
```

Правила:

- `dictionary_code` и `table_name` не меняются после создания.
- `fields` — дополнительные поля сверх `value_code` и `name`.
- Порядок `fields` сохраняется и используется при генерации колонок.
- `value_code` и `name` всегда обязательны.
- Дополнительные поля по умолчанию nullable.
- `string` имеет длину; по умолчанию 500, максимум 4000.
- `integer`, `bigint`, `date`, `uuid` длину не имеют.
- Описание полей неизменно для справочника. Изменение состава полей требует нового справочника.
- `dictionary.JSON_metadata` — текущее описание.
- `dictionary_version.JSON_metadata` — копия на момент версии.

## 4. Таблица данных

### 4.1. Шаблон

Для каждого справочника создаётся отдельная таблица:

```sql
CREATE TABLE "wall_material" (
    version_id  integer      NOT NULL,
    value_code  varchar(64)  NOT NULL,
    name        varchar(500) NOT NULL,
    parent_code varchar(500) NULL,
    PRIMARY KEY (version_id, value_code)
) PARTITION BY LIST (version_id);
```

Обязательные колонки:

| Колонка | Тип | Ограничение |
|---|---|---|
| `version_id` | `integer` | `NOT NULL` |
| `value_code` | `varchar(64)` | `NOT NULL` |
| `name` | `varchar(500)` | `NOT NULL` |

Дополнительные колонки:

- Имя — `code` из `fields`.
- Тип — по таблице соответствия.
- `NULL` или `NOT NULL` — по `nullable`.
- Порядок — как в `fields`.

Соответствие типов:

| `type` | PostgreSQL |
|---|---|
| `string` | `varchar(length)` |
| `integer` | `integer` |
| `bigint` | `bigint` |
| `date` | `date` |
| `uuid` | `uuid` |

Первичный ключ — `(version_id, value_code)`. Суррогатный ключ строки не используется. `value_code` уникален внутри версии.

Внешние ключи на другие справочники в v2 не создаются: форма их не описывает.

### 4.2. Секция версии

Для каждой версии создаётся отдельная секция:

```sql
CREATE TABLE "wall_material_4"
    PARTITION OF "wall_material"
    FOR VALUES IN (4);
```

Правила:

- Имя секции: `{table_name}_{version_id}`.
- Секция создаётся при загрузке версии.
- Секция удаляется только архивацией, не удалением строк.
- `DEFAULT`-секция не создаётся.
- Родительская таблица существует без секций до первой версии.

### 4.3. Вставка

```sql
INSERT INTO "wall_material" (version_id, value_code, name, parent_code) VALUES
    (4, 'BRICK', 'Кирпич', NULL),
    (4, 'AERATED', 'Газобетон', 'BRICK');
```

Правила:

- Вставка идёт пачками до 1000 строк.
- Порядок строк — порядок файла.
- Строковые литералы экранируются: `'` удваивается, переводы строк заменяются пробелом.
- Даты пишутся как `DATE 'YYYY-MM-DD'`.
- `NULL` пишется как `NULL`.
- Имена таблиц и колонок заключаются в двойные кавычки.
- Значения не подставляются в SQL без экранирования.

## 5. Чтение

### 5.1. Выбор версии

Действующая версия:

```sql
SELECT dictionary_version_id, version_id, status, valid_from, valid_to, table_name
FROM dictionary_version
WHERE dictionary_id = $1
  AND status = 'active';
```

Версия на дату:

```sql
SELECT dictionary_version_id, version_id, status, valid_from, valid_to, table_name
FROM dictionary_version
WHERE dictionary_id = $1
  AND valid_from <= $2
  AND (valid_to IS NULL OR valid_to >= $2)
ORDER BY version_id DESC
LIMIT 1;
```

Версия по номеру:

```sql
SELECT dictionary_version_id, version_id, status, valid_from, valid_to, table_name
FROM dictionary_version
WHERE dictionary_id = $1
  AND version_id = $2
  AND status IN ('active', 'closed');
```

Черновик по номеру не читается.

### 5.2. Признак архива

```sql
SELECT to_regclass(
    format('public.%I', table_name || '_' || version_id)
) IS NULL AS archived;
```

`archived: true` означает, что секция отсоединена. Строка каталога остаётся.

### 5.3. Значение

```sql
SELECT value_code, name
FROM "wall_material"
WHERE version_id = $1
  AND value_code = $2;
```

Для архивированной версии запрос к таблице не выполняется: сразу возвращается `result = archived`.

### 5.4. Страница

```sql
SELECT value_code, name
FROM "wall_material"
WHERE version_id = $1
  AND ($2::varchar IS NULL OR value_code > $2)
ORDER BY value_code
LIMIT $3;
```

Курсор — последний `value_code` предыдущей страницы. Он непрозрачен для клиента.

### 5.5. Проверка кодов

```sql
SELECT value_code, name
FROM "wall_material"
WHERE version_id = $1
  AND value_code = ANY($2::varchar[]);
```

Отсутствующие коды получают `result = absent`.

## 6. Создание справочника

Порядок:

1. Проверить `dictionary_code`, поля и уникальность кода.
2. Построить `JSON_metadata`.
3. Вычислить `table_name`.
4. Начать транзакцию.
5. Вставить строку в `dictionary`.
6. Записать SQL-файл в `db/sql-schema`.
7. Выполнить SQL-файл.
8. Зафиксировать транзакцию.

При ошибке на шагах 5–7 транзакция откатывается. SQL-файл, если он уже создан, остаётся на диске.

Имя таблицы:

- `WallMaterial` → `wall_material`.
- `OwnershipType` → `ownership_type`.
- `OKTMO` → `oktmo`.
- Разделитель — `_`, все буквы строчные.

Уникальность:

- `dictionary_code` уникален без учёта регистра.
- Имя таблицы производно от кода, поэтому отдельная уникальность не нужна.
- Если таблица с таким именем уже существует, создание завершается `script_failed`.

## 7. Загрузка версии

Порядок:

1. Начать транзакцию.
2. Заблокировать строку `dictionary` через `SELECT ... FOR UPDATE`.
3. Проверить, что справочник активен.
4. Вычислить `version_id = max(version_id) + 1`.
5. Проверить `valid_from` относительно действующей версии.
6. Вставить черновик в `dictionary_version`.
7. Записать SQL-файл в `db/sql-data`.
8. Создать секцию.
9. Вставить строки пачками.
10. Закрыть прежнюю действующую версию.
11. Перевести новую версию в `active`.
12. Зафиксировать транзакцию.

При любой ошибке транзакция откатывается. SQL-файл остаётся.

Закрытие прежней версии:

```sql
UPDATE dictionary_version
SET status = 'closed',
    valid_to = $1::date - 1
WHERE dictionary_id = $2
  AND status = 'active';
```

Активация новой версии:

```sql
UPDATE dictionary_version
SET status = 'active',
    valid_from = $1
WHERE dictionary_version_id = $2;
```

Проверка даты:

- Если действующая версия есть, `valid_from` новой версии должен быть строго позже `valid_from` действующей.
- Иначе — `invalid_valid_from`.
- Для первой версии ограничение только на корректность даты.

## 8. Архивация

```sql
ALTER TABLE "wall_material"
    DETACH PARTITION "wall_material_2";
```

Правила:

- Архивировать можно только закрытую версию.
- Строка `dictionary_version` не удаляется.
- Секция отсоединяется и больше не участвует в чтении.
- Признак `archived` вычисляется через `to_regclass`.
- Повторная архивация не меняет состояние.
- Архивированная версия недоступна для скачивания.
- Сервисный API возвращает `archived: true` и не отдаёт строки.

## 9. SQL-файлы

### 9.1. Каталоги

| Каталог | Что содержит |
|---|---|
| `db/sql-schema` | SQL создания таблицы справочника |
| `db/sql-data/{table_name}` | SQL создания секции и вставки строк версии |

Имена:

```text
db/sql-schema/2026.10.23 16.00.00 - wall_material.sql
db/sql-data/wall_material/2026.10.23 16.10.00 - wall_material.sql
```

### 9.2. Правила

- Кодировка UTF-8 без BOM.
- Время — локальное, с точностью до секунды.
- Если файл с таким именем уже есть, добавляется суффикс `-2`, `-3` и так далее.
- Сначала файл пишется целиком, затем выполняется.
- Файл не удаляется при ошибке выполнения.
- Повторный запуск с тем же путём не перезаписывает файл.
- Путь возвращается в ответе API для диагностики.

### 9.3. Транзакции

- Транзакцией управляет приложение, а не SQL-файл.
- SQL-файл выполняется в уже открытой транзакции; отдельные `BEGIN` и `COMMIT` в файл не пишутся.
- Ошибка выполнения откатывает изменения.
- Каталог и физическая таблица меняются в одной транзакции, где это возможно.
- DDL в PostgreSQL транзакционен, поэтому создание таблицы и запись паспорта можно откатить вместе.
- SQL-файл остаётся на диске и после отката, чтобы ошибку можно было разобрать.

---

## 10. Ограничения и допущения

- v2 работает с простыми списками: одна таблица на справочник.
- `schema_name` зарезервирован для наборов таблиц, но API и UI v2 их не создают.
- Максимум 50 дополнительных полей.
- Максимум 100 МБ на файл загрузки.
- Максимум 1000 строк в одной пачке вставки.
- `dictionary_code` — до 63 символов, `dictionary_name` — до 200.
- `table_name` после преобразования кода — до 63 символов.
- `value_code` — до 64 символов, `name` — до 500.
- Строковые поля — до 4000 символов.
- Один экземпляр PostgreSQL, без реплик и шардирования.
- Резервное копирование и мониторинг в v2 не описываются.
