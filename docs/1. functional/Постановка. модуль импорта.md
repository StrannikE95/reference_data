# Постановка: модуль импорта

Модуль читает JSON, который интеграционный модуль уже положил в Kafka, и пишет SQL-файл. Форматы XSD, CSV и ZIP он не разбирает: состав таблиц и строки приходят готовыми. Правила разбора — в `Постановка. интеграционный модуль.md`. Как секция устроена в PostgreSQL — в `Секционирование.md`.

Запрос задаёт действие. Тело запроса и JSON прогона связаны полем `loadId`.

```json
{
  "loadId": "6f1c0a2e-7b14-4d2a-9c31-0a6e5d8b41f2",
  "operation": "fill-section",
  "dictionaryCode": "AssBuilding",
  "versionId": 13
}
```

`operation`:

- `create-tables` — по сообщению из `dictionary.integration.metadata` собрать SQL создания таблиц нового справочника;
- `fill-section` — по одному или нескольким сообщениям из `dictionary.integration.data` собрать SQL заполнения новой секции уже существующего справочника.

`versionId` обязателен для `fill-section`. В JSON источника этого номера нет: его назначает модуль справочников и передаёт в запросе. Для `create-tables` номер не нужен: создаётся родительская таблица без секции и без строк.

Если в `dictionary.integration.result` по этому `loadId` есть ошибка, SQL не пишется.

Результат — один файл UTF-8 без BOM в каталоге из настройки `Import:SqlDirectory`: `{loadId}.sql`. Ответ запроса — путь к файлу. Исполнение файла остаётся вызовом `psql`.

Общие правила текста SQL:

- Имена таблиц берутся из JSON. К ним добавляются только поля секции, перечисленные ниже.
- Строковый литерал: `'` удваивается. Перевод строки в значении заменяется пробелом.
- Дата пишется `DATE 'yyyy-MM-dd'`.
- Тип из метаданных: `string` с `length` → `varchar(n)`, `integer` → `integer`, `bigint` → `bigint`, `date` → `date`, `uuid` → `uuid`.
- Повтор ключа внутри одного `loadId` — `duplicate_code`, файл удаляется.
- Пустые `rows` при `fill-section` — `empty`, файл удаляется.

## Создание таблиц

Берётся одно сообщение метаданных этого `loadId`.

К каждой таблице добавляется ключ секции. Для простого списка это `version_id integer NOT NULL` и `simple_dictionary_table_id uuid NOT NULL`. Для набора ГАР — только `version_id`. Первичный ключ JSON дополняется слева `version_id`. У простого списка в первичный ключ также входит `simple_dictionary_table_id`, а ключ из JSON становится `UNIQUE` вместе с `version_id`. Внешний ключ дополняется `version_id` с обеих сторон: строка секции ссылается на строку той же секции.

Родительская таблица создаётся с `PARTITION BY LIST (version_id)`. Секция и `INSERT` в этот файл не входят.

Назначение здания, сообщение метаданных с таблицей `ass_building`:

```sql
CREATE TABLE ass_building (
    version_id                   integer NOT NULL,
    simple_dictionary_table_id   uuid NOT NULL,
    value_code                   varchar(12) NOT NULL,
    name                         varchar(500) NOT NULL,
    PRIMARY KEY (version_id, simple_dictionary_table_id),
    UNIQUE (version_id, value_code)
) PARTITION BY LIST (version_id);
```

Материал стен добавляет `parent_code` и связь на ту же таблицу:

```sql
CREATE TABLE wall_material (
    version_id                   integer NOT NULL,
    simple_dictionary_table_id   uuid NOT NULL,
    value_code                   varchar(12) NOT NULL,
    name                         varchar(500) NOT NULL,
    parent_code                  varchar(12) NULL,
    PRIMARY KEY (version_id, simple_dictionary_table_id),
    UNIQUE (version_id, value_code),
    FOREIGN KEY (version_id, parent_code)
        REFERENCES wall_material (version_id, value_code)
) PARTITION BY LIST (version_id);
```

ОКТМО:

```sql
CREATE TABLE oktmo (
    version_id                   integer NOT NULL,
    simple_dictionary_table_id   uuid NOT NULL,
    value_code                   varchar(11) NOT NULL,
    section                      varchar(1) NOT NULL,
    name                         varchar(500) NOT NULL,
    parent_code                  varchar(11) NULL,
    change_number                varchar(10) NOT NULL,
    introduced_on                date NOT NULL,
    PRIMARY KEY (version_id, simple_dictionary_table_id),
    UNIQUE (version_id, value_code, section),
    FOREIGN KEY (version_id, parent_code, section)
        REFERENCES oktmo (version_id, value_code, section)
) PARTITION BY LIST (version_id);
```

ГАР — схема и две таблицы. Строки JSON не переименовываются.

```sql
CREATE SCHEMA gar;

CREATE TABLE gar.object_level (
    version_id   integer NOT NULL,
    level_code   varchar(10) NOT NULL,
    name         varchar(250) NOT NULL,
    short_name   varchar(50) NOT NULL,
    PRIMARY KEY (version_id, level_code)
) PARTITION BY LIST (version_id);

CREATE TABLE gar.addr_obj (
    version_id    integer NOT NULL,
    object_id     bigint NOT NULL,
    object_guid   uuid NOT NULL,
    name          varchar(250) NOT NULL,
    type_name     varchar(50) NOT NULL,
    level_code    varchar(10) NOT NULL,
    start_date    date NOT NULL,
    end_date      date NOT NULL,
    PRIMARY KEY (version_id, object_id),
    FOREIGN KEY (version_id, level_code)
        REFERENCES gar.object_level (version_id, level_code)
) PARTITION BY LIST (version_id);
```

Повторный `create-tables` на уже созданной таблице останавливается на `CREATE TABLE`. Таблица справочника создаётся один раз.

## Заполнение секции

Берутся все сообщения данных этого `loadId`. Секция создаётся на первом сообщении. Следующие сообщения того же прогона дописывают строки в ту же секцию. `last: true` закрывает файл.

Имя секции — имя таблицы и `versionId` из запроса: `ass_building_13`.

```sql
CREATE TABLE ass_building_13
    PARTITION OF ass_building FOR VALUES IN (13);

INSERT INTO ass_building (version_id, simple_dictionary_table_id, value_code, name) VALUES
    (13, gen_random_uuid(), '204001000000', 'Нежилое'),
    (13, gen_random_uuid(), '204002000000', 'Жилой дом'),
    (13, gen_random_uuid(), '204003000000', 'Многоквартирный дом'),
    (13, gen_random_uuid(), '204004000000', 'Жилое строение');
```

`gen_random_uuid()` заполняет `simple_dictionary_table_id`: во внешнем файле этого идентификатора нет. Порядок строк — порядок `rows`, затем порядок `part`.

Материал стен и ОКТМО пишутся так же. Родитель в JSON уже стоит раньше ребёнка, дополнительно модуль порядок не меняет. `INSERT` режется пачками по 1000 строк, по одной пачке на сообщение. `TRUNCATE` родительской таблицы в файл не входит: секция добавляется рядом с уже загруженными версиями.

Для ГАР в одном прогоне две таблицы. Сначала секция уровней и её строки, затем секция адресных объектов. Так внешний ключ находит уровень в той же версии.

```sql
CREATE TABLE gar.object_level_13
    PARTITION OF gar.object_level FOR VALUES IN (13);

INSERT INTO gar.object_level (version_id, level_code, name, short_name) VALUES
    (13, '8', 'Элемент улично-дорожной сети', 'Улица');

CREATE TABLE gar.addr_obj_13
    PARTITION OF gar.addr_obj FOR VALUES IN (13);
```

Адресных строк слишком много для одного `INSERT` на весь срез. Каждое сообщение `addr_obj` становится отдельным `INSERT` на свои строки (не больше 1000). Файл SQL из-за этого большой; он собирается потоком, целиком в память не читается.

`skippedLevel` из последнего сообщения данных в SQL не входит. Это уже учтённые пропуски интеграционного модуля.

Запуск готового файла:

```text
psql -d dictionaries -f C:\out\6f1c0a2e-7b14-4d2a-9c31-0a6e5d8b41f2.sql
```
