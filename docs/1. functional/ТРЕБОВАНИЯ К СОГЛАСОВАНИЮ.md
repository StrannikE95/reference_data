Для юристов договора: **1. Общие требования к документации**  
**1.1. Нормативная база.** Документация разрабатывается в соответствии с ГОСТ 34.601-90, ГОСТ 34.201-89, ГОСТ 34.602-89, РД 50-34.698-90. Для документов по информационному обеспечению и базе данных применяется ГОСТ 24.205-80. Для текстовых документов — ГОСТ 2.105-95 и ГОСТ 2.106-96.  
**1.2. Оформление и язык.** Документация на русском языке. Отчетные материалы передаются на бумажном носителе (А4, А3) и в электронной форме на неизменяемом оптическом носителе (CD-R/DVD-R). Электронные форматы: doc, rtf, vsd, ppt, xml, а также исходные форматы инструментов проектирования (при наличии).  
**1.3. Передача исходных текстов.** Для программного обеспечения передаются исходные тексты с контрольными суммами MD5 для каждого файла, инструкция по сборке и исполняемые файлы (при наличии).  
**2. Техническое описание системы**  
Документ должен содержать: назначение системы и ее место в бизнес-процессах заказчика; функциональные требования по компонентам с привязкой к версиям; требования к надежности и производительности (целевые показатели доступности, времени отклика, сохранности данных при сбоях); описание технологических пользователей и их прав.  
**3. Системный ландшафт микросервисов**  
Документ описывает архитектуру в микросервисном стиле и включает:  
**Логическую архитектуру**: перечень микросервисов, зоны ответственности, границы доменов.  
**Взаимодействие компонентов**: схемы синхронного (API) и асинхронного (брокеры сообщений) обмена. Взаимодействие через общую базу данных исключается — только через программные интерфейсы или обмен сообщениями.  
**Диаграмму системного ландшафта** (например, в нотации C4): внутренние системы, внешние системы, границы контуров (DEV, TEST, PROD).  
**API-спецификации**: для каждого межсервисного вызова — метод, формат данных, ссылка на документацию; для недокументированных методов — полное описание.  
**Требования к наблюдаемости**: каждый сервис предоставляет эндпоинты для проверки здоровья (health, readiness, liveness) и публикует метрики в формате Prometheus или JSON.  
**4. Проектные решения (Design Documentation)**  
Документация по каждому компоненту/сервису должна содержать:  
**Диаграммы процессов** в нотации BPMN с фиксацией вызовов базы данных, ожидаемого поведения и полного текста выполняемых запросов.  
**UML-диаграммы** для описания обмена данными с другими системами с указанием метода обмена.  
**Описание конфигурации**: параметры баз данных, настройки среды, схема развертывания.  
**Методы мониторинга и параметры** для отслеживания состояния компонента.  
**План отката (roll-back)** на предыдущую версию с указанием ограничений.  
**5. Протоколы тестирования**  
Протоколы функционального и интеграционного тестирования содержат: дату формирования, состав участников, повестку и принятые решения; перечень проверенных сценариев (тест-кейсов) и результаты; для каждого дефекта — описание, severity, статус, ссылку на задачу в трекере; итоговое заключение о соответствии системы требованиям технического задания. Испытания проводятся с учетом ГОСТ 34.603-92.  
**6. Нагрузочное тестирование**  
Подрядчик передает **Методику нагрузочного тестирования** и **Отчет о результатах**. Отчет включает:  
**Объект испытаний**: перечень бизнес-процессов, подвергнутых нагрузке.  
**Протоколы запусков** с детализацией по времени отклика.  
**Параметры нагрузки**: количество виртуальных пользователей, профиль нагрузки, интервалы измерений, общее число транзакций.  
**Результаты**: достигнутые показатели производительности, максимальная пропускная способность, перечень выявленных «узких мест».  
**Рекомендации** по донастройке программно-аппаратного комплекса.  
**Набор артефактов**: нагрузочные скрипты, эмуляторы/заглушки, конфигурации тестового стенда.  
Тестирование проводится на обезличенном тестовом стенде заказчика, не на промышленном контуре.  
**7. Спецификация объектов БД и модель данных**  
Документация выполняется в соответствии с **ГОСТ 24.205-80** и включает три уровня описания.  
**7.1. Концептуальная модель.** E/R-диаграмма с описанием сущностей и связей на предметном уровне.  
**7.2. Логическая модель.** Детализация сущностей: атрибуты, типы данных, ограничения целостности, ключи (первичные, внешние). Нотация — IDEF1X или UML-диаграмма классов.  
**7.3. Физическая модель (спецификация объектов БД).** Для каждой таблицы: имя и назначение; перечень полей (имя, тип, размер, обязательность, значение по умолчанию, смысловое описание); индексы, ограничения (CHECK, UNIQUE, FOREIGN KEY); схема данных на физическом уровне.  
Дополнительно передаются **словарь данных** и **DDL-скрипты** создания объектов. Физическая модель должна быть воспроизводима из DDL-скриптов без ручных правок.  
**8. Описание сборки CI/CD и публикации**  
Документ должен обеспечивать полную воспроизводимость конвейера сборки и развертывания силами заказчика.  
**8.1. Архитектура CI/CD.** Описание используемых инструментов (GitLab CI/CD), их версий и ролей. Схема взаимодействия компонентов конвейера: репозиторий, система сборки, реестр артефактов, среды развертывания.  
**8.2. Описание этапов пайплайна (pipeline).** Для каждого этапа (build, test, package, deploy) указываются: назначение, входные и выходные артефакты, команды и конфигурационные файлы, критерии успешного завершения. Конвейер должен включать автоматический запуск при внесении изменений в ветку кода и генерацию артефакта релиза.  
**8.3. Управление артефактами и версионированием.** Описание процедуры сборки Docker-образов, публикации в registry, версионирования и подписи артефактов. Правила присвоения версий (например, тег, равный хешу коммита).  
**8.4. Инструкция по настройке и запуску.** Пошаговое руководство с командами, конфигурационными файлами и ключевыми шагами, включая настройку CI/CD для сред разработки и production. Описание возможных ошибок и способов их устранения, а также ограничений и предположений.  
**8.5. Логирование и метрики.** Настройка базового логирования процесса сборки и развертывания, вывод ключевых метрик (время сборки, статус тестов, результат развертывания) и сохранение логов для анализа сбоев. Измерение времени выполнения каждого этапа и предложения по оптимизации (параллелизация, кэширование зависимостей).  
**9. Техническое описание масштабирования**  
Документ должен содержать формализованную стратегию масштабирования системы и отдельных сервисов.  
**9.1. Модель масштабирования.** Для каждого сервиса указывается поддерживаемый тип масштабирования — горизонтальный, вертикальный или комбинированный. Для горизонтально масштабируемых сервисов задаются минимальное и максимальное количество экземпляров. Для сервисов, где вертикальное масштабирование ограничено требованиями соответствия, фиксируются предельные размеры инстанса.  
**9.2. Метрики и политики автомасштабирования.** Для каждого автомасштабируемого сервиса определяются: целевая метрика (CPU, Request Rate, длина очереди и т.п.), пороговые значения для scale-up и scale-down, время «остывания» (cooldown). Пример: сервис заказов — CPU > 70% или Request Rate > 500/сек; сервис каталога — CPU > 60%.  
**9.3. Масштабирование уровня данных.** Описание стратегии масштабирования баз данных: количество read-replicas, размер пула соединений на экземпляр сервиса, стратегия шардирования (при наличии).  
**9.4. Требования к доступности при масштабировании.** Для каждого сервиса указываются целевой SLA, RPO и RTO, а также стратегия обеспечения отказоустойчивости (active-passive, active-active, backup restore). Документ должен подтверждать, что выбранная стратегия масштабирования не снижает целевые показатели доступности.  
**9.5. Ограничения и предположения.** Фиксируются архитектурные и инфраструктурные ограничения, влияющие на масштабирование (например, требования compliance, ограничения сети, квоты облачной платформы), а также предположения, при которых стратегия масштабирования остается работоспособной.  
**10. Приемка документации**  
Документация считается принятой, если: комплектность соответствует ГОСТ 34.201-89 и перечню, согласованному сторонами; документы прошли нормоконтроль и не имеют критических замечаний; электронные версии верифицированы по контрольным суммам, указанным в акте передачи; для баз данных физическая модель воспроизводима из предоставленных DDL-скриптов без ручных правок; конвейер CI/CD воспроизводим по предоставленной инструкции на инфраструктуре заказчика; стратегия масштабирования подтверждена результатами нагрузочного тестирования.
