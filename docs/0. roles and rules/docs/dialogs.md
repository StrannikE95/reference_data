## Общее

+ Структура и формат одинаковые у однотипных документов. Содержание тоже одинаковое: в документе нет ничего лишнего.
+ Описание API повторяет пример из `C:\_utils_\Obsidian\БД - Знания\🗃️ Артефакты (архив)\3. Работа\Документация\Сервисы`.
+ Описание БД повторяет `C:\_code_\api_authentication_jwt\docs\templates\db.md`: та же структура документа и тот же состав разделов.
+ Текст на русском. Имена полей, путей и кодов остаются как в контракте.
+ Алгоритм — это текст шагов, не код.
+ Если метод пишет промежуточный JSON или SQL, в алгоритме указано, куда. Если не пишет — это тоже сказано прямо.

## `API.md`

Оглавление методов и общие коды. Описание одного метода живёт в своём файле.

Раздел `# Функционал`. Таблица:

+ `Проект` — крайний левый столбец. Значения: `admin`, `service`.
+ `Контроллер`
+ `Метод` — полный вызов, глагол и путь: `GET /admin/dictionaries/{dictionary_code}/versions/{version_id}`
+ `Описание` — короткая ссылка на файл метода, как в примере

Столбец `Тип` из примера в таблицу не входит.

Раздел `# Коды ответов` остаётся, как в примере: код состояния, код ошибки, расшифровка, описание.

Файл метода лежит по пути `проект/контроллер/метод`.

## Файл метода

Одинаковые разделы:

+ ссылка на главную
+ `# Описание` — полный вызов и что делает метод
+ `# Входные параметры` — имя, место (`path`, `query`, `body`, `form`), обязательность
+ поля успешного ответа. Секция не называется «Параметры ответа»: параметры бывают у запроса
+ `# Алгоритм работы`

Для `management.api` алгоритм состоит из двух частей:

+ `Валидация`. Проверки входящих данных без бизнес-условий: тип, значение по регулярному выражению, существование объекта по переданному идентификатору, существование переданного элемента списка. Несовместимость параметров с данными в БД, которая выясняется по ходу метода, сюда не входит. Диаграмм у этого блока нет.
+ `Бизнес-логика`. Диаграмма есть.

## `DB.md`

Состав как в шаблоне:

+ заголовок схемы
+ ER-диаграмма mermaid
+ на каждую таблицу: короткий текст, таблица `Поле / Тип / Ограничения / Назначение`, индексы и ограничения, правила работы
+ связи между таблицами

## `UI.md`

+ Документ описывает экраны. Вызовы API, тела запросов и коды ответов в него не входят.
+ У каждой формы есть макет прямо в этом markdown-файле, в предпросмотре. Отдельно макет не открывают.
+ На макете видны все отображаемые данные, все поля ввода и все кнопки. Дизайн не важен: макет нужен, чтобы проверить функциональную часть.
+ Фон макета слегка серый, чтобы окно не сливалось с фоном документа.
+ Разделов «Что отображается» нет.
+ Блок действий экрана «Данные версии» — обычный текст без номера.

## Одно и то же во всей папке

+ Владелец вводится при создании и показывается в списке и на экране версий. Паспорт меняется в отдельном окне.
+ Публикация в одной транзакции делает черновик действующим и закрывает прежнюю действующую версию.
+ Дата конца при закрытии действующей версии равна дате выполнения этого закрытия. На экране её не вводят.
