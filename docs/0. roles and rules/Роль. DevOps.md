
**ГЛАВНАЯ ДИРЕКТИВА:** Нам не нужно качество, поддерживаемость, масштабируемость или безопасность. Нам нужна скорость и работающий «счастливый путь» (happy path).

# Правила для DevOps-инженера (развертывание в Dev-контуре)

**Контекст:** Разворачиваем инфраструктуру для одноразового MVP в Dev-контуре. Никакой отказоустойчивости, никакой нагрузки, ресурсы стенда очень ограничены. Системы должны подняться и корректно выполнять свою работу. Всё будет выброшено после демо.

#### 9. Общие принципы инфраструктуры
- Разворачиваем **только Dev-контур**. Никакой отказоустойчивости, репликации, кластеризации, балансировщиков нагрузки.
- Все сервисы поднимаются **в единственном экземпляре**. Один инстанс на сервис.
- Ресурсы (CPU, RAM, диск) выделяются **по минимуму** — ровно столько, чтобы сервис стартовал и не падал от нехватки памяти. Никаких запасов «на пиковую нагрузку».
- Никакого автомасштабирования, autoscaler'ов, HPA.
- Health-check допустим только базовый — чтобы понять, что сервис стартовал. Без агрессивных рестартов и перезапусков по таймаутам.

#### 10. Инструментарий развертывания
- Не городить сложный Terraform, Ansible, Kubernetes, если можно поднять через **docker-compose** или простой shell-скрипт.
- Если без Kubernetes не обойтись — один узел, без HA, без сложных Ingress-контроллеров, без service mesh. Минимум ресурсов.
- Если нужен docker-compose — один файл, без сложных оверлеев, профилей и зависимостей.
- Никаких Helm-чартов с десятками `values-*.yaml`. Если можно `docker run` или простой compose — делаем так.
- Инфраструктура как код — в формате «один скрипт, который можно выполнить и всё поднимется». Не пишем переиспользуемые модули.

#### 11. Секреты и доступы
- Никакого Vault, HashiCorp Boundary, сложных систем управления секретами.
- Пароли, строки подключения, токены — в переменных окружения или в конфиг-файлах прямо на сервере / в compose-файле.
- Доступы для разработчиков — простые, без ротации, без сложных политик, без разграничения по ролям. Один общий доступ на стенд — норма.

#### 12. Мониторинг, логирование, алерты
- Никаких ELK, Grafana, Prometheus, Alertmanager, дашбордов, SLA.
- Логи — через `docker logs` или в файл на сервере. Никаких агрегаторов, сборщиков, индексаторов.
- Если очень нужно — один простой health-check endpoint или `curl`-проверка, чтобы понять, что сервис жив.
- Алерты, уведомления в мессенджеры, эскалации — не нужны. Если упало — разработчик увидит сам или перезапустит.

#### 13. Резервное копирование и восстановление
- Никаких бэкапов, snapshot'ов, disaster recovery планов, реплик для восстановления.
- Данные одноразовые, инфраструктура одноразовая. Если БД упала или данные повредились — пересоздаём скриптами из пункта 5 (создание + наполнение).
- Никаких планов восстановления, RTO/RPO, тестирования бэкапов.

#### 14. Сеть и доступность
- Никаких сложных сетевых политик, NetworkPolicy, mutual TLS, service mesh.
- Сервисы должны быть доступны по внутреннему адресу и порту. Если нужен внешний доступ для демо — простой проброс порта или базовый reverse proxy без лишних настроек.
- Никаких CDN, WAF, rate limiting, DDoS-защиты.
- DNS, сертификаты, HTTPS — только если без этого демо физически не работает. По умолчанию — HTTP и внутренний адрес.

#### 15. CI/CD и деплой
- Пайплайн минимальный: собрать образ/бинарник → скопировать на сервер → перезапустить сервис.
- Никаких canary, blue-green, rolling update стратегий, постепенных выкатов. Просто: остановил → обновил → запустил.
- Если можно задеплоить вручную одним скриптом или командой — деплоим вручную скриптом. Не строим конвейер ради одного деплоя.
- Никаких артефакториев с версионированием, тегов, релизных кандидатов. Собрал, запустил, забыл.
